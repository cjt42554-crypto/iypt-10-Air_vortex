# 工作、验证与晋升规则

## 1. 普通任务工作流

1. 按本目录 README 的顺序完成必读和 Git 实时核验。
2. 明确任务目标、允许写入范围、来源基线、成功条件和停止条件。
3. 默认只在 `未提交修改/当前任务/**` 中修改；成熟目录仅作只读参照。
4. 开始前更新或确认 `管理/变更映射.md` 与 `管理/验收清单.md`。
5. 小步实现并把重要判断写入 `管理/修改记录.md`。
6. 按风险执行验证，把命令、环境、提交/源码身份、返回码、证据位置及未执行项写入 `管理/验证记录.md`。
7. 检查差异只落在授权范围，确认成熟 tree SHA 未变。
8. 阶段成果直接在 `main` commit；需要跨机器或交给网页版 Pro 时，push 到 `origin/main`，并记录实际结果。

## 2. 最低验证要求

不同变更至少满足下列证据：

| 变更类型 | 最低验证 |
|---|---|
| 纯目录/文档整理 | 文件清单、相对链接、旧到新映射、Git rename/diff、成熟 tree SHA |
| 启动入口或路径调整 | 从仓库根和候选根分别执行帮助或自检；验证不依赖旧绝对路径 |
| 程序修复 | 直接相关测试、回归测试、失败反例和运行入口；记录环境与跳过项 |
| 数值或物理模型 | 单元/量纲/守恒检查、完整运行、几何与活动集检查、收敛/残差/不确定度；不得只给相邻采样 |
| 实验比较 | 预注册协议、校准/验证隔离、观测算子身份、原始数据来源、盲验证与不确定度 |

历史结果只能标为历史结果。若当前源码、配置、环境或提交身份不同，必须说明未复验，不能继承 PASS。

## 3. Git 规则

- 仓库只允许 `main`。不得创建、保留或 push 功能分支、审查分支和临时分支；文件夹结构承担全部阶段管理。
- `未提交修改` 与 `git status` 没有同义关系；工作区应保留完整 Git 历史。
- commit 前检查 `git diff --check`、授权范围和验证记录。
- commit/push 前确认当前分支为 `main`，upstream 为 `origin/main`，并核验远端 URL、待推送提交和工作树状态。
- 每次交接确认本地 `refs/heads/*` 和远端 `refs/heads/*` 都只有 `main`。
- 未实际成功 push 时，不得说 GitHub 已更新。
- 不重写、删除或覆盖历史机器证据；更正以新文件或新记录追加，并引用原证据身份。

## 4. 晋升到成熟基线的硬门

晋升不是普通开发步骤。必须同时满足：

1. 用户明确授权本次晋升及目标目录；
2. 候选范围冻结，来源基线和候选提交 SHA 明确；
3. `变更映射.md` 逐项列出候选源、成熟目标、操作和理由；
4. `验收清单.md` 的必需项全部通过，没有用删测试、缩小采集或放宽阈值换取 PASS；
5. `验证记录.md` 有当前候选身份对应的机器证据和人工审查结论；
6. 所有 NO-GO、跳过项、外部依赖和残余风险已显式处理或由用户接受；
7. 晋升前再次记录三个成熟目录 tree SHA，并保留可恢复的提交；
8. 晋升后运行结构、链接、入口、测试和 tree 复核，更新控制区状态；
9. 晋升使用 `main` 上独立、可审查的 commit，并 push 到 `origin/main`。

晋升应只把变更映射中批准的内容回写到 `01`–`03`，不能把整个工作区、缓存、临时结果或审查草稿一起复制过去。候选工作区在晋升验收完成前不删除。

## 5. 回退与异常

出现失败时保留日志和失败证据，状态写为 FAIL、NO-GO、PARTIAL 或 UNKNOWN。回退必须绑定明确提交或 tree SHA，优先用新提交恢复；除非用户明确要求，不执行破坏性历史重写。

成熟 tree 漂移、错误晋升或证据与源码身份不一致时，停止后续晋升，记录差异并请求用户决定。
