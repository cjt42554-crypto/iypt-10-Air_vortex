## 2. 独立代码结论：性能问题真实存在

当前正式 HF3D 热循环的大部分物理算子仍由 NumPy 主机数组执行，包括相输运、界面压缩、动量输运、黏性、表面张力、边界松弛、旋转系、拓扑与大量诊断。CUDA 只承担压力投影。

正式 CUDA 压力类已经提供 `project_device()`，其接口允许 GPU 驻留数组并明确说明不需要主机全场传输；但正式 HF3D `stepper.py` 当前调用的是 `projection.project()`。该 host-array wrapper 每次压力求解会把速度、密度和初始压力上传到设备，并把三分量速度和压力下载回主机。`pressure.py` 的运行元数据也明确登记 `host_device_transfer_each_solve = true`。

因此现有架构是：

```text
主机 NumPy 物理算子
→ 多个全场数组 H2D
→ CUDA 压力投影
→ 多个全场数组 D2H
→ 主机 NumPy 后处理与下一步
```

用户提供的约 1.01 个 CPU 核、GPU 多数时间 16%--22% 和 CPU time 约等于 wall time，与该结构一致。它足以确认：

```text
CURRENT_HF3D_EXECUTION_IS_HOST_SERIAL_OR_HOST_MEMORY_PATH_LIMITED
GPU_IS_RECURRENTLY_STARVED
THREAD_ENVIRONMENT_VARIABLES_ALONE_CANNOT_FIX_THE_ARCHITECTURE
```

这不是“程序已经充分利用 32 线程”的状态，后续必须治理。

## 3. 是否立即中断当前 S2

### 3.1 裁决：不立即中断

```text
INTERRUPT_CURRENT_G9_DT2_FOR_PERFORMANCE = NO
CONTINUE_CURRENT_G9_DT2 = YES
IF_S2_PASS, RUN_CURRENT_AUTHORIZED_S3 = YES
```

理由不是否认性能问题，而是当前时点尚未满足“停止并优化能够显著缩短本次端到端交付时间”的实测门。

### 3.2 端到端盈亏

G9_DT1 与 G9_DT0 的墙钟比为约 `1.964`，与时间步数约翻倍一致。按这一已观测比例，G9_DT2 完整运行约为 `1.56e4 s`；在 `0.006/0.010` 时，剩余量级约为：

```text
remaining current G9_DT2 ≈ 6.26e3 s ≈ 1.74 h
```

任何正式程序或候选实现修改都会使当前精确快照授权失效。R1 合同又要求六个算例在同一清洁执行提交上全新生成，禁止跨提交轨迹拼接。因此停止后不能只重跑 G9_DT2，也不能保留 G9_DT0/G9_DT1 作为新分类输入。

仅按已经实测的 G9 三个算例估算，旧实现的基准工作量约为：

```text
G9_DT0 + G9_DT1 + estimated G9_DT2
≈ 3982 + 7821 + 2*7821
≈ 27445 s
```

要在约 `6257 s` 的当前剩余时间内完成“优化、验证、重新裁决、全新重跑”，即使完全忽略 G6 三算例、开发时间、等价性验证和再授权，优化后 G9 三算例也必须已经实测达到超过约 `4.39x` 的端到端加速。计入 G6、验证和治理后，实际盈亏门显著更高。

当前只有利用率和旧运行耗时，没有可运行的优化候选、成对端到端基准、数值等价证明或超过 `4.39x` 的实测加速。因此：

```text
PERFORMANCE_DEFECT = CONFIRMED
IMMEDIATE_STOP_BREAK_EVEN = NOT_DEMONSTRATED
```

把“空闲核心很多”直接推断为“现在停机一定更早完成”是不成立的。线程数、环境变量或理论峰值都不是端到端性能证据。

### 3.3 当前停止还存在证据风险

当前运行器在普通异常上会保存 `partial.npz` 并提交失败事务，但 Python 的 `KeyboardInterrupt` 继承自 `BaseException`，不属于代码捕获的 `Exception`。直接 Ctrl+C、SIGINT 或外部终止不能保证进入现有 partial/summary/ledger 事务。

因此当前实现没有一个已经预注册并测试的“在登记输出边界优雅中止并提交完整 S2 中断证据”的入口。此时主动中断可能只留下 stdout 中的最近进度，而没有与台账一致的 G9_DT2 partial。该证据风险进一步支持让当前最后算例自然完成。

### 7.3 允许探索的方法

不预设唯一技术路线。允许比较并择优：

- 将 HF3D 热状态与工作数组保持 GPU 驻留，只在登记输出和最终归档边界回传；
- 使用 `project_device()` 并消除当前每步完整场往返；
- GPU 化相输运、动量、黏性、表面张力、边界和诊断热点；
- kernel fusion、预分配、内存池、固定拓扑缓存和临时数组复用；
- 可确定性 CPU 多线程、Numba/OpenMP/TBB/Cython 或等价后端；
- 在证明内存容量和无相互干扰后，并行执行彼此独立的 benchmark case；
- 受控的 CPU/GPU 流水与传输重叠，但必须在所有语义边界显式同步；
- 降低 Python 调度和对象分配开销；
- 增加未来只在登记时刻响应的优雅停止机制。

### 7.4 明确禁止

性能优化不得：

- 修改物理方程、边界条件、G0 几何、材料参数或驱动；
- 修改网格、时间步、输出时刻、诊断窗口或六算例矩阵；
- 放宽压力容差、CFL、散度、守恒、clip/repair、完成性或证据门；
- 减少诊断、跳过拓扑检查、延迟失败检查或少写归档换速度；
- 使用 FP32、TF32、混合精度、`fastmath`、近似算子或更少迭代换速度；
- 改变预条件器、CG 停止语义或浮点规约顺序后仍声称“同一实现”而不做新身份裁决；
- 用 checkpoint、V1/R1 raw 或已观察轨迹作为新科学运行的初态；
- 只设置 `OMP_NUM_THREADS`、`MKL_NUM_THREADS`、CPU affinity 或 GPU clocks 就宣称通过性能门；
- 只给 kernel microbenchmark，不给完整端到端基准；
- 为追求高利用率而使墙钟变慢。

### 8.2 基准集合

固定采用与 D3R1 相同物理输入、正式 G0 和质量门，仅为性能测试缩短 `run.duration_s`：

```text

```

同时报告不含首次 JIT/编译的 steady-state throughput，但推广判据以完整端到端墙钟为主。

B4 至少执行一次基线和一次候选。若使用当前已完成的 G9_DT0 作为基线，必须证明环境、配置、执行入口和计时边界一致；若候选结果距离速度阈值小于 10%，必须重新成对运行 B4，不能依赖历史温度状态不同的单次计时。

## 9. 数值等价门

性能候选分为两类，不能混淆。

### 9.1 E0：严格实现等价

只有满足 E0，才允许把候选称为同一正式 HF3D 的纯性能替换：

1. 配置 canonical hash、网格、G0 掩膜和初态逐 dtype/shape/byte 相同；
2. 接受/拒绝序列、每步 `dt`、limiter、retry、压力迭代数和事件序列逐项相同；
3. 登记输出时刻逐 `uint64` 相同；
4. 在 G6/G9 的第 1、8、64、512 个接受步和 B4 终点，所有状态数组逐元素、逐字节相同；
5. 稠密诊断数组、登记观测量和 archive payload 在排除明确的时间戳/性能元数据后逐字节相同；
6. CPU 参考、现有 CUDA 参考和候选路径的既有正式测试全部通过；
7. 失败注入、事务回滚和证据门保持相同。

若候选只改变数据驻留、传输、缓存或无语义调度，E0 是默认要求。

### 9.2 E1：数值接近但非逐位等价

若 GPU 化或多线程规约改变浮点顺序而不能满足 E0，不得直接替换并声称 D3R1 连续执行。必须：

```text
new backend/model identity
new source-tree identity
new protocol (at least D3R2)
new result-blind equivalence contract
new numerical qualification
all scientific cases fresh from zero
```

E1 最低门在看到新科学结果前冻结，至少包括：

- 相同步数、时间步、重试、事件和硬门分类；
- 所有状态有限，守恒/散度/压力/CFL 不恶化；
- 每个登记观测量的候选--参考差异低于该观测量冻结尺度地板的 1%，且相对差异低于 `1e-8`（取较宽者仍须预注册）；
- D3 指标相对最近分类阈值的安全裕度不被优化误差吞噬；
- 至少一个完整 G6 和 G9 生产等价窗通过独立重载。

E1 通过只证明新后端数值上可比较，不自动证明物理或实验正确。

## 10. 实际加速门与资源利用门

正式推广必须同时满足：

```text
B1--B3 geometric-mean median speedup >= 1.75x
B1, B2, B3 each median speedup >= 1.50x
B4 end-to-end speedup >= 1.75x
no case wall-time regression > 5%
projected six-case D3 campaign speedup >= 1.75x
```

短基准三次样本中的最慢候选不得比相应基线中位数慢超过 10%，并报告离散度；不允许只挑最快一次。

资源利用不是速度的替代品，但必须证明已经消除当前稳定单核饥饿模式。至少满足以下一类：

```text
GPU-resident path:
  median GPU compute utilization >= 45%
  p90 GPU utilization >= 70%
  full-field H2D/D2H bytes per step reduced >= 75%

CPU-parallel path:
  steady aggregate CPU utilization >= 400%
  no single thread长期承担几乎全部 CPU 工作

hybrid path:
  profiler shows >= 70% wall time inside parallel CPU/GPU kernels,
  and the end-to-end speed gate passes
```

若算法本身达到速度门但利用率不满足以上数字，Codex 可提交 profiler 证明硬件受内存带宽、依赖链或问题规模限制，停止交 Pro 裁决；不得自行忽略利用率门。

## 11. 正式提升与新授权

### 11.1 当前 D3R1 正常完成时

当前 D3R1 应先按旧快照完成并冻结。性能优化不得事后替换该结果，也不要求为了性能重新跑已经完整、合法的 D3R1。

优化完成后：

- E0 通过：可申请正式纯性能提升；提升后用于未来算例，不回写当前 D3R1；
- 只有 E1：保留现有正式参考路径，新加 accelerated backend 身份，进入 D3R2/新的数值资格。

### 11.2 当前序列自然失败或被迫外部中断时

旧授权立即失效，旧完成/部分算例全部不可拼接。候选通过性能与等价门后必须：

1. 提交清洁实现、基准、等价报告和新正式源码树；
2. Pro 独立静态复核；
3. 新裁决提交作为 reviewed parent；
4. 唯一授权子提交只修改新的授权对象；
5. 新协议使用全新证据根；
6. S0、六算例和 S3 全部从零执行；
7. 每阶段显式检查，任一失败原样停止。

若正式源码树发生任何变化，现有 `be349aec...` 授权不能恢复；必须签发绑定新源码树和新实现 blob/hash 的新授权。

## 12. 停止条件与结论上限

性能阶段任一情况出现即停止交 Pro：

- 端到端加速未达门；
- E0/E1 等价门失败；
- 硬门、事件或失败事务改变；
- 需要扩大正式修改范围；
- 新依赖不可复现；
- GPU/CPU 数值不确定性未解释；
- 基准受热降频或后台负载污染；
