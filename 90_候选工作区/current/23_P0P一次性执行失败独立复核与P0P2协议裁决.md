## 3. 独立代码路径重建

### 3.1 Claim 为什么已经不可逆消费

执行器在每个样本前先做完整环境门。第一个环境门通过后，执行器按顺序：

```text
create_claim_and_ledger()
mark_sample_running(sequence_index=0, sample_id=WARMUP_B1)
execute_one_sample()
```

`create_claim_and_ledger()` 以独占创建写入唯一 claim，并初始化固定 18 项 ledger。`mark_sample_running()` 随即把第 0 项从 `NOT_STARTED` 改为：

```text
state = RUNNING
start_count = 1
launch_token_sha256 = one-time token hash
```

因此，当 worker 随后失败时，协议已经跨过 claim 与首次样本启动边界。失败是否发生在第一步数值推进之前，不改变 V1 的消费事实。

异常路径把第 0 项转成 `FAILED_STOPPED`，把顶层 ledger 转成 `FAILED_STOPPED`，再独占发布 `execution_failure.json`。状态机明确拒绝：

```text
second claim
second start of WARMUP_B1
start of WARMUP_B2
failure replacement
completion publication after failure
resume / retry / supplement / replacement
```

所以本次 claim 不得复活；WARMUP_B1 不得改名为“未真正开始”，其余 17 项也不得在 V1 下继续。

### 3.2 Worker 在哪里失败

Worker 在启动后先完成一次性 launch token、PID/锁身份和外部 monitor release 校验；随后进入 `run_sample()`。

`run_sample()` 先生成并写出 `effective_config.json`。随后 `prepare_runtime()` 再次取得同一有效载荷，并执行：

```python
config = SimulationConfig.from_dict(payload)
```

正式 `SimulationConfig.__post_init__()` 对无实测转速时序的配置执行：

```text
if drive.ramp_duration_s > run.duration_s:
    raise ConfigError("drive ramp duration cannot exceed run duration")
```

由于 `0.005 > 0.002`，异常在网格、压力投影、初态、零步诊断和 `_ACTIVE_RUNTIME` 建立之前发生。因而：

```text
partial_evidence = null
worker stdout = empty
HF3D step count = 0
```

是代码路径的必然结果，而不是证据缺失或失败处理不完整。

### 3.3 不是 B1 偶发故障

B1、B2、B3 分别来自：

```text
G6_DT0
G9_DT0
G9_DT2
```

三份源配置均满足：

```text
source run.duration_s = 0.010
drive.ramp_duration_s = 0.005
actual_speed_schedule_time_s = []
```

旧 P0-P 合同对三类 benchmark 全部只允许：

```text
run.duration_s: 0.010 -> 0.002
```

因此三份有效配置都会被正式配置类确定性拒绝。WARMUP_B1 只是固定顺序中第一个暴露共同缺陷的样本；不能据此把 B2/B3 标为“尚可能通过”。

## 4. 失败性质裁决

本次失败分类为：

```text
PRE_NUMERICAL_PROTOCOL_CONFIGURATION_INVALID
```

更具体地说，它是**候选性能协议的派生配置合同错误**：

- 冻结合同选择了不满足正式配置不变量的短窗；
- `effective_config()` 只证明“仅一个叶字段发生变化”，没有证明变化后的对象仍是合法 `SimulationConfig`；
- 正式程序正确拒绝了不可能在运行结束前完成的驱动爬升。

本次失败不是：

```text
HF3D numerical instability
projected-divergence failure
pressure solver failure
CFL failure
CUDA fallback
GPU/CPU/thermal environment failure
monitor or profiler failure
archive/reload failure
formal physics-model failure
measured performance regression
```

没有任何 HF3D 接受步、性能样本或 profiler 样本完成。因此不存在可用于热点排序、CPU/GPU 利用率归因、端到端吞吐估计或 P1 加速设计的 P0-P 测量结果。

正式 `SimulationConfig` 的跨字段校验不应被删除、放宽或绕过。错误位于候选 P0-P 设计和其 preclaim 静态门，而不位于正式配置模型。

## 5. 静态门为何漏检

这是一次实质静态审查遗漏，不能用“运行时才知道”解释。该反例在 claim 前完全可判定。

### 5.1 合同层只验证身份，没有验证语义可构造性

`load_contract()` 核对合同 ID、文件哈希、三份 source hash、固定 schedule、唯一允许变化字段和其他冻结身份；它不把派生 payload 交给正式配置类。

### 5.2 `effective_config()` 只验证差异集合

旧实现检查：

```text
leaf differences == {"run.duration_s"}
```

但“只改一个字段”不蕴含“修改后仍满足所有跨字段约束”。这里恰好破坏：

```text
drive.ramp_duration_s <= run.duration_s
```

### 5.3 单元测试复现了同一盲区

三 benchmark 测试仅调用 `effective_config()` 并断言差异集合为 `{run.duration_s}`，没有调用：

```python
SimulationConfig.from_dict(effective_payload)
```

所以测试证明了变更范围，却没有证明配置合法。

### 5.4 零步静态审计与 preflight 没有覆盖固定日程配置

静态审计覆盖授权拒绝、事务、分配观察器、合成数值等价、Nsight 能力、环境负例和 source identity。它没有对 B1/B2/B3 的派生配置做正式构造。

动态授权后的 `zero_step_preflight()` 也只检查：

```text
contract
numerical-quality binding
P0-D / Pro evidence
authorization
raw-root hygiene
instantaneous environment
```

它没有物化 18 项 schedule 的三份唯一有效配置，也没有进行正式 config round-trip。因此 preflight 全门通过与首个 worker 配置失败并不矛盾；它说明 preflight 的门集不完整。

### 5.5 精确 Git 绑定只能冻结错误，不能证明正确

Review-binding material 和 `I → P → C` 拓扑精确证明了：

```text
执行的是被审查的那些字节
```

但没有证明：

```text
这些字节生成的每份派生输入在语义上可执行
```

密码学身份绑定不能替代领域不变量检查。

### 5.6 前次 Pro 复核责任

先前裁决对授权拓扑、一次性消费、无恢复事务、worker 隔离和证据原子性审查是成立的；但对派生配置可构造性审查不足。以下旧结论从本裁决起撤回其操作效力：

```text
P0-P V1 dynamic executability accepted
existing P0-P runtime needs no further correction
V1 fixed 18-item schedule is executable
```

以下结论继续保留：

```text
claim is single-use
failed schedule is terminal
sample replacement/resume is prohibited
failure transaction is fail-closed
formal source and formal config guard remain protected
```

旧裁决文件作为历史记录原样保留，不后验改写。

另有一个非本次直接原因的门语义缺口：`zero_step_preflight()` 的顶层 `gate_pass` 没有合并 `environment_gate_pass`。本次用户已核实环境全门通过，所以它不改变本次因果结论；P0-P2 仍必须消除该双重“通过”语义。

## 7. 是否存在合法的新一代协议路径

结论：**存在，但必须是实质独立的 P0-P2；不存在 V1 的合法恢复、重跑、补样或换名续跑路径。**

P0-P2 合法性的必要条件是：

```text
new contract ID
new schedule ID and canonical hash
new authorization ID
new parent ticket and exact authorization child
new grant nonce
new raw root
new claim and ledger
new sample IDs
new effective-config hashes
zero use of V1 partial/state/trajectory/archive/sample prefix
```

V1 只能作为：

```text
failure evidence
negative regression
protocol-design input
```

不能作为 P0-P2 的 warm-up、完成前缀、时间样本、性能测量或 claim 配额。

为保持统计结构可比，P0-P2 可以保留 V1 的 18 项逻辑顺序，但每个样本都必须使用新的 `P0P2_` 命名空间，并由新的 schedule object 重新绑定；旧样本目录、launch token、manifest 或 ledger 条目不得被引用。

这不是“给失败样本第二次机会”。它是基于已发现的、可审计的合同缺陷，在任何新动态数据产生前重新预注册的另一项工程诊断。

## 8. P0-P2 零步设计冻结边界

### 8.1 有效短窗

P0-P2 的三类 benchmark 继续读取同一三份 source config，并继续只允许修改：

```text
run.duration_s
```

新的统一短窗冻结为：

```text
run.duration_s = 0.005
drive.ramp_duration_s = 0.005  # 保持源配置，不修改
output_interval_s = 0.001
registered output times =
  [0.000, 0.001, 0.002, 0.003, 0.004, 0.005]
```

选择 `0.005 s` 的理由：

1. 它是保持原驱动爬升不变时满足正式不变量的最短窗口；
2. 它不需要第二项物理配置修改；
3. 它避免把已知约 `0.0092 s` 才出现的 D3R1 G9_DT2 数值失败强行纳入性能基线；
4. 它仍只用于工程性能归因，不产生 D3 科学分类或装置预测。

禁止把 `drive.ramp_duration_s` 后验缩为 `0.002 s`，也禁止绕过正式配置校验。

### 8.2 Claim 前的权威可构造性门

新 preflight 必须在创建 lock、raw、claim、ledger 或样本目录之前，对 B1/B2/B3 三份唯一有效 payload 全部执行：

```text
source hash verification
only run.duration_s changed
SimulationConfig.from_dict(effective_payload)
config.to_dict() exact round-trip
canonical effective-config SHA-256 binding
drive ramp/schedule coverage invariants
registered output schedule compatibility
formal source identity binding
```

三份有效配置的 canonical SHA-256 必须写入新合同、静态证据和未来父票据。不能只绑定 source hash。

还必须提供每个 benchmark 的独立 fresh-process、零接受步构造探针，至少覆盖：

```text
formal imports
exact effective config
actual CUDA selection without fallback
exact grid construction
pressure engine construction
initial state
zero-step diagnostics and initial frame
clean teardown
hf3d_time_steps_advanced = 0
```

这些探针不是 warm-up，不保存或复用状态，不提供 scored timing；探针后必须重新通过冷却/环境门，动态样本仍从全新进程和全新初态开始。

### 8.3 新 preflight 的统一通过语义

P0-P2 只允许一个顶层布尔：

```text
gate_pass =
  contract
  and evidence
  and authorization
  and source/config constructibility
  and zero-step exact-case construction
  and raw-root hygiene
  and environment
```

不得再出现“顶层 PASS 但 environment_gate_pass=false”的状态。任何环境或配置门失败均在 claim 前原样停止且不创建运行根。

### 8.4 必须新增的回归反例

至少包括：

```text
V1 payload: duration 0.002, ramp 0.005
  -> formal ConfigError before claim

P0-P2 payload: duration 0.005, ramp 0.005
  -> formal config round-trip PASS

任一 B1/B2/B3 有效配置非法
  -> whole schedule preclaim FAIL

effective payload 多改一个字段
  -> FAIL

source/effective canonical hash drift
  -> FAIL

旧 V1 raw、claim、ledger 或 sample 被作为输入
  -> FAIL

新 raw root 与 V1 raw root 相同或重叠
  -> FAIL

preflight failure creates lock/raw/claim/ledger/sample output
  -> FAIL

V1 terminal ledger 被恢复、复制为新 ledger 前缀或改写
  -> FAIL
```
