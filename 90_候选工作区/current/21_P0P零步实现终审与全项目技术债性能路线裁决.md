## 2. P0-P 零步实现终审

### 2.1 可接受的部分

提交 `8a0c2fa...` 的 P0-P 零步实现总体可接受。以下核心语义成立：

1. **默认拒绝授权。** `p0p_execution_authorization.json` 为严格 `NOT_AUTHORIZED`，无 child/self commit 或 blob 自引用字段。
2. **父票据精确授权模型。** 授权审计按 `I -> P -> C` 拓扑检查单父关系、父票据、精确 denied/authorized blob、review-only delta 和 `P..C` 唯一授权文件变化。
3. **NUL-safe Git plumbing。** 关键路径使用 `ls-tree -z`、`diff-tree --raw -z` 和 `cat-file`，不会重现中文路径 quoting 假阴性。
4. **一次性消费。** 非消费 preflight 与 `O_CREAT|O_EXCL` execution claim 分离；claim 后禁止 resume、补样、替换或第二次 claim。
5. **固定 schedule。** 18 个样本的顺序、模式、配置和 scored 属性被冻结，orchestrator 不提供 `--skip`、`--repeat`、`--start-at`、`--resume` 等绕过入口。
6. **worker 隔离。** worker 要求有效 claim、独占锁、expected sequence index 和一次性 launch token；直接调用被拒绝。
7. **环境门。** 每个样本前检查 AC、32 个在线逻辑 CPU、governor、其他计算进程、30 秒背景 CPU、CPU/GPU 温度、GPU 计算进程和工具链身份。当前约 96.875 °C 的 Tctl 被正确拒绝且不消费 claim。
8. **端到端样本语义。** worker 从零构造正式配置、网格和初态，执行正式 HF3D stepper、全部硬门、帧记录、archive 写入、严格重载和最终 GPU 同步；不使用旧轨迹或 checkpoint。
9. **跨模式数值同一。** timed、HOST、CUDA、MEMORY 模式通过 canonical numerical payload SHA-256 比较，排除时间和 profiler 元数据后要求逐位同一。
10. **主机热点证据。** cProfile 与透明 operator-boundary 包装分工明确，嵌套区间使用 exclusive 归因；98% 顶层覆盖、90% solver 归因及 unknown 区间负例均有机器门。
11. **CUDA 证据。** 只使用已验证的 `nsys --trace=cuda,nvtx --sample=none --cpuctxsw=none`，要求 `.nsys-rep`、SQLite、四份 stats、NVTX 尾部、PID/context、kernel/API/memcpy 和方向/字节交叉一致。
12. **分配证据。** 主机观察器覆盖已声明的 glibc heap/aligned/mmap API，并有 known-count、exit 和 overflow 探针；设备侧组合 CuPy allocator recorder、pool 高水位、CUDA allocation API 和显存监测。
13. **原子证据事务。** sample staging、原子目录发布、claim/ledger/failure/complete 事务、symlink 和并发写入负例均存在。
14. **零步静态证据。** 已提交静态审计记录 30/30 授权测试、36/36 harness/regression tests、正式源码不变、P1 未实现、0 时间步和 0 样本。

因此，本轮不要求回退或重写当前 P0-P runtime implementation。

### 2.2 结论边界

该 harness 测量的是：

```text
D3R1 production-equivalent HF3D execution path
= fresh construction + formal HF3D stepping + D3 hard gates
  + frame/archive/reload + final synchronization
```

它不是整个 GUI/CLI 应用的通用交互性能基准。后续报告可以写成“D3/HF3D 生产等价短窗基线”，不能扩大成“整个桌面程序端到端性能已被完整覆盖”。

主机 allocator 的结论也必须写成：

```text
observed forwarded glibc heap/aligned/mmap allocation APIs
```

不能声称已经证明所有第三方运行库、驱动内部和不可见设备分配的绝对全集。只有结合 RSS、CuPy pool、CUDA API、nvidia-smi 和 unmatched-allocation 门后，才构成当前合同下足够的工程归因。

## 6. 全项目技术债裁决

### 6.1 总结

三选一裁决：

```text
不重构：拒绝
全项目大范围推倒重写：拒绝
局部重构：接受
```

这里的“局部重构”不是只改一个函数，而是：

```text
TARGETED CROSS-MODULE REFACTOR
```

即围绕已被证据确认的高耦合和性能路径，实施分阶段、可回退、显式身份的跨模块重构；不改写整个项目。

### 6.2 为什么不需要大范围重写

正式 HF3D 已经完成过结构拆分，当前职责基本清晰：

```text
backends/high_fidelity_3d.py   运行编排
hf3d/stepper.py                单步事务
hf3d/pressure.py               压力后端选择
hf3d/timestep.py               时间步控制
hf3d/recording.py              诊断与结果组装
hf3d/types.py                  状态和诊断类型
numerics/*                     离散算子
io/archive.py                  严格归档
```

正式源码树有广泛测试、冻结证据和明确身份。全量重写会同时改变浮点规约、事件顺序、错误事务、archive 语义和科学证据身份，迫使所有数值资格重新建立，风险和迁移成本远高于收益。

GUI、forward theory、archive 等较大模块目前没有被实际缺陷或性能证据证明需要重写。仅凭文件较大，不足以授权大范围重构。

### 6.3 必须局部重构的关键证据

#### A. HF3D 性能架构债：P0，最高优先级

真实运行显示：

```text
16 cores / 32 threads
process CPU ≈ 101%
main thread ≈ 99.9%
GPU mostly ≈ 16%--22%
process CPU time ≈ wall time
```

正式热循环的大多数算子仍在 NumPy 主机数组上执行，CUDA 主要用于 pressure projection；热循环调用 host wrapper `projection.project()`，每次求解发生完整场 H2D/D2H。GPU 处于周期性饥饿，CPU 多核也基本闲置。

这是结构性性能债，不是环境变量问题。

#### B. campaign/evidence 基础设施重复：P1，第二优先级

候选工作区已经出现多套体量较大的：

```text
runner
analyser
stage machine
authorization audit
claim/ledger/failure transaction
source/config/raw identity
atomic evidence publisher
```

D1、D2、D3、P0-P 分别复制和演化同类逻辑。过去已经出现路径 quoting、自引用授权、S0/S1 前置、S3 发布事务等多次证据链缺陷，说明重复实现正在增加维护风险。

但历史冻结证据不得回写。应在当前 P0-P 和下一次科学 campaign 之间抽取一个新的共享 `campaign_evidence` 核心，供未来任务使用；旧脚本保持只读。

#### C. recording/archive 与设备驻留边界：P1/P2

当前 recording 和 archive 假设主机 NumPy 状态。GPU 驻留路径若继续复用现有边界，会被迫频繁回传完整场。需要把：

```text
step-local diagnostic reduction
registered-frame extraction
full-state final archive
live preview
```

分离为显式同步边界。

#### D. 平台构建物和 profiler 工具：P2

P0-P 提交了当前平台的 allocator `.so` 和合成 probe 证据，这对绑定本机执行可接受；但未来共享基础设施应采用可复现构建清单和源码/构建物双 hash，而不是把一个平台二进制误当作通用发行物。

### 6.4 重构优先级

```text
Priority 0: 完成 P0-P baseline/profiler，冻结现状
Priority 1A: HF3D accelerated backend 架构
Priority 1B: 未来 campaign/evidence 共享核心
Priority 2: recording/archive/device-boundary 分层
Priority 3: GUI/forward/其他大模块，仅在有独立缺陷证据时处理
```

在 P0-P 完成前，不得修改正式程序。否则会失去当前 baseline 的身份价值。

## 7. 硬件利用裁决

### 7.1 当前利用不充分

裁决：

```text
CPU utilization adequacy = FAIL
GPU utilization adequacy = FAIL
end-to-end efficiency = FAIL
```

单进程约一个逻辑 CPU、主线程近满载、其余 31 个逻辑 CPU 基本空闲，同时 GPU 大部分时间只有 16%--22%，不符合“充分利用本机性能”。线程环境变量即使设为 2 或 32，也不会自动并行 Python/NumPy stencil 和对象调度，不能解决 CPU 主路径与 GPU pressure 脉冲之间的架构断裂。

### 7.2 主要技术路线

主要路线裁决为：

```text
EXPLICIT GPU-RESIDENT HF3D BACKEND
NUMERICAL IDENTITY CLASS = E1 by default
```

不把它作为当前 backend 的静默优化开关，而建立显式新身份，例如：

```text
high_fidelity_3d_cuda_resident_v1
```

理由：真正消除当前瓶颈通常需要将 phase、face velocities、pressure、density、viscosity和工作数组长期保留在设备，GPU 化相输运、界面压缩、动量、黏性、表面张力、边界、诊断 reduction，并只在登记输出和最终归档边界回传。此类迁移几乎必然改变浮点求值和规约顺序，强行称为 E0 bitwise replacement 不可信。

当前 reference backend 必须保留，作为数值和失败事务基准。

### 7.3 次要路线

允许并行探索两类候选，但必须在 P0 后由实测热点决定：

1. **E0 低风险候选**：预分配、临时数组复用、固定拓扑缓存、减少 Python 对象和无语义同步、只读 metadata 缓存。只有逐位相同才可提升。
2. **CPU 并行候选**：Numba/OpenMP/Cython/TBB 或等价实现。适用于 P0 证明主机 stencil 占主导且 GPU 显存或迁移成本不利的情况。

禁止先验认定“GPU 一定更快”或“32 线程一定更快”；以完整端到端数据选择。

## 8. 性能重构迁移计划

### Phase 0：基线冻结

完成当前 P0-P：B1/B2/B3 timed + HOST/CUDA/MEMORY profile。不得开始 P1。

### Phase 1：候选原型，正式路径之外

在候选区建立两个最小原型：

```text
A: E0 cache/preallocation candidate
B: E1 GPU-resident candidate
```

若 P0 表明 CPU 并行更有希望，再建立 C。不得同时把三条路线全部提升到正式路径。

### Phase 2：内存和算子迁移

GPU 路径先做数组 liveness/峰值预算。RTX 5060 当前总显存约 8.05 GB，要求：

```text
peak device memory <= 80% of available VRAM
至少保留 20% 安全余量
无 OOM、无池无限增长、无长期 thermal/power throttle
```

迁移顺序：

```text
设备状态与 workspace
→ pressure project_device
→ phase/interface
→ momentum/viscosity/body forces
→ boundary/topology reductions
→ registered frame/diagnostic extraction
→ final archive transfer
```

每一步都必须有 reference differential tests，不能到最后才比较。

### Phase 3：数值等价与失败事务

E0 逐位门通过后才可称纯性能替换。E1 必须建立新 backend ID、新 formal source identity、新结果盲合同和至少 D3R2 的新科学协议。

### Phase 4：成对端到端性能门

不得只给 kernel microbenchmark。必须包含进程启动、构造、步进、硬门、记录、归档、重载和同步。

### Phase 5：正式提升

Pro 独立复核后才允许：

- E0：替换或新增严格等价 fast path；
- E1：并列保留 reference 与 accelerated backend；
- 新科学运行使用全新 S0、全新证据根和精确授权。

## 10. 实际硬件利用率验收

### GPU-resident 路径

同时要求：

```text

p90 GPU utilization >= 70%
full-field H2D/D2H bytes per accepted step reduced >= 75%
不再出现稳定的“单主线程满载、GPU 等待”模式
peak device memory 满足 20% 余量
```

### CPU-parallel 路径

同时要求：

```text

至少 4 个逻辑 CPU 持续承担有效工作
任一线程 CPU time 不超过总线程 CPU time 的 50%

```

### Hybrid 路径

```text
profiler 证明 >= 70% wall time 位于并行 CPU/GPU kernel
并同时通过端到端速度门
```

利用率不是速度替代品。若速度门通过但利用率数字未达到，必须提交 profiler 证明受内存带宽、依赖链或问题规模限制，并停交 Pro，不得自行豁免。

## 11. 端到端加速验收

### E0 候选

沿用冻结性能门：

```text
B1/B2/B3 各自 median speedup >= 1.50x
B1--B3 geometric-mean median speedup >= 1.75x
B4 production-equivalent complete window >= 1.75x
B5 complete G9_DT2-to-failure >= 1.75x
projected six-case campaign speedup >= 1.75x
无 benchmark regression > 5%
```

### E1 候选

由于引入新 backend 身份、重新数值资格和全新科学运行，正式提升收益门提高为：

```text
B1/B2/B3 各自 median speedup >= 1.50x
B1--B3 geometric-mean median speedup >= 2.00x
B4 >= 2.00x
projected six-case campaign speedup >= 2.00x
无 benchmark regression > 5%
```

未达到该收益，不值得承担新后端迁移和重新验证成本。

## 12. campaign/evidence 共享核心重构要求

性能 backend 稳定后，允许从未来任务中抽取共享库，但必须遵守：

1. 旧 D1/D2/D3/P0 证据和脚本保持不可变；
2. 新库只服务未来 campaign；
3. 模块边界建议为：

   ```text
   git/source/config binding
   parent-ticket authorization
   claim/lock/schedule ledger
   sample transaction
   strict archive/evidence manifest
   telemetry/profiler adapters
   ```

4. 每次迁移一个未来 campaign，并做旧实现/共享核的状态机和故障注入差分；
5. 不通过抽象化放宽任何科学合同；
6. 若共享核不能减少重复或测试面，停止重构。

## 13. 风险与停止条件

任一情况出现即停止并交 Pro：

```text
P0-P review material 生成需要修改 runtime
P0-P 样本在未授权时启动
正式源码在 baseline 前变化
GPU 候选显存无 20% 余量
候选改变物理方程、门值或输出
E0 出现任何位差
E1 误差合同在看到科学结果后修改
硬件利用率提高但端到端变慢
benchmark 受热降频或其他进程污染
formal promotion 需要删除 reference backend
共享基础设施迁移会改写旧证据
```
