## 3. 剩余阻塞项

### P0-1：S1 没有机器要求 S0 台账已经提交为 PASS

`command_run_stage(stage)` 当前只要求目标阶段为 `NOT_EXECUTED`；当目标为 S2 时额外要求 S1 `PASS`，但当目标为 S1 时没有要求 S0 台账项已经是：

```text
disposition = EXECUTED
status = PASS
```

与此同时，`execution_identity_audit(require_fresh=False)` 分别检查：

- S0 报告存在、`gate_pass = true` 且执行提交匹配；
- 阶段台账整体语义和证据检查通过。

它没有把“S0 报告存在”与“台账 S0 已提交为 PASS”交叉绑定。全 `NOT_EXECUTED` 的初始台账本身是合法状态，因此以下中断序列可进入真实 S1：

1. `prepare-execution` 写入全 `NOT_EXECUTED` 台账；
2. S0 网格和初态审计完成并写入有效 S0 报告；
3. 进程在把 S0 台账项提交为 `EXECUTED/PASS` 之前异常终止；
4. 重新调用 `run-stage --stage S1`；
5. S0 报告门通过，全 `NOT_EXECUTED` 台账也通过独立语义门；
6. 运行器开始准备并推进 `G6_DT0`，但台账仍声明 S0 未执行。

S1 最终写 PASS 时，严格状态机可能才拒绝该非法序列；此时真实 HF3D 时间步已经推进，失败发生得过晚。

**裁决：阻塞。** 在任何算例准备或时间推进之前，必须由统一阶段前置门证明所有前驱阶段均处于精确的已执行通过状态。

### P0-2：前置条件拒绝会先写全局失败标记，再尝试非法台账转换

顶层异常处理目前会把所有 `prepare-execution` 或 `run-stage` 异常交给 `_record_dynamic_failure()`。该函数先写入：

```text
artifacts/runs/execution_failure.json
```

随后才调用 `_replace_stage_entry()` 把对应阶段改成 `FAILED_STOPPED`。

考虑在 S0 已通过、S1 尚未执行时误调用 S2：

1. `command_run_stage("S2")` 正确抛出 `S2 requires S1 PASS`；
2. 顶层捕获异常并调用 `_record_dynamic_failure("S2", ...)`；
3. 全局失败标记先成功写入；
4. 台账随后尝试从 `[S0 PASS, S1 NOT_EXECUTED, S2 NOT_EXECUTED, S3 NOT_EXECUTED]` 转为 `[S0 PASS, S1 NOT_EXECUTED, S2 FAILED, S3 NOT_EXECUTED]`；
5. 严格状态机正确拒绝越过 S1 的 S2 失败状态；
6. 结果是失败标记已经存在，而台账仍声明没有失败阶段。

该状态会阻止后续运行，却不能由台账解释，违反“全局失败对象、阶段状态与证据路径必须同义”的目标。P0-1 的孤立 S0 报告场景也可能触发同类不一致。

操作顺序错误、前驱阶段未通过、目标阶段已执行等属于**前置条件拒绝**，不是已经启动阶段后的数值或执行失败。前置拒绝应在创建或修改 raw 证据之前结束；只有统一前置门已经通过、阶段正式进入可执行事务之后的异常，才应提交失败状态。

**裁决：阻塞。** 失败事务不能先写不可回滚的全局标记，再验证对应台账转换是否合法。

   - 目标阶段已执行、重复调用或前驱证据路径错误时为无副作用拒绝；
