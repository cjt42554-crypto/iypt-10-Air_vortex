## 2. 可以保留的实现

本轮不要求推倒或重写 V2 主体。以下设计和实现可保留。

### 2.1 合同、配置和日程

- V2 使用独立 contract、schedule、authorization、claim、ledger 和 sample namespace；
- 三份配置只把 `run.duration_s` 改为 `0.005`，保持 `drive.ramp_duration_s=0.005`；
- B1/B2/B3 已正式 `SimulationConfig.from_dict()` 和精确 `to_dict()` 往返；
- 原生输出时刻采用冻结向量的整数索引，不再重复浮点累加；
- 18 项顺序固定为 3 个 warm-up、9 个 scored timed 和 B2/B3 各三个 profile 子运行；
- CLI 没有 skip、only、repeat、start-at、resume、补样或替换入口。

### 2.2 授权拓扑

未来授权审计已经实现：

```text
git fetch --no-tags origin main
symbolic HEAD = refs/heads/main
HEAD = origin/main
C2 exactly one parent P2
P2 exactly one parent reviewed snapshot
NUL-safe raw diff
path / status / mode / old-new blob validation
exact denied and authorized blobs
reviewed implementation/static/contract/capability binding
```

ticket、ruling、current、history 的 review-only 路径集合和 `100644` mode 也被明确约束。该方向成立。

### 2.3 生产等价数值路径

Worker 在数值导入前验证授权、一次性 launch token、活锁所有者和 PID start ticks；随后：

- 先导入正式 `airvortex` 以应用线程策略；
- 使用正式 HF3D grid、pressure backend、initial state、stepper 和 retry/rollback；
- 每个接受步执行 D3R1 适用硬门；
- 按冻结时刻索引记录 6 个 frame；
- 完成 result assembly、archive write、strict reload、canonical numerical payload 和 final CUDA sync；
- TIMED、HOST、CUDA、MEMORY 通过 canonical payload 进行逐位同一检查。

### 2.4 Profile 和样本事务

- unprofiled、HOST、CUDA、MEMORY 四种模式相互排斥；
- scored 样本不启用 profiler 或 allocator interposer；
- HOST 使用 cProfile 和透明语义区间；
- CUDA 只使用已验证的轻量 Nsight 配置；
- MEMORY 使用 native allocator observer、CuPy recorder 和显存/RSS 交叉；
- 每个样本先写 staging，再以 `renameat2(RENAME_NOREPLACE)` 发布 success 或 failure 目录；
- claim、ledger、worker token 和 sample target 都禁止第二次使用。

以上主体足以作为补丁基础，不应重新复制成另一套并行活动实现。

## 3. 阻塞项 P0-1：授权票据的当前工具链/主机身份仍在 claim 后才完全核验

### 3.1 当前顺序

授权后的 campaign preflight 会：

```text
验证 ticket 与 reviewed capability manifest 一致
检查当前温度、CPU 数量、governor 一致性和 GPU 空闲
运行三个当前环境 zero-step probe
```

但它没有把**当前**环境与 ticket 绑定的完整 capability identity 做同一比较。

Worker 在 claim 和 `mark_sample_running()` 之后才检查：

```text
GPU driver/runtime/name/UUID
GPU Python realpath and package versions
CPU model
full affinity
exact governors map
AC records
formal thread policy
```

### 3.2 可触发反例

例如静态证据绑定的所有 governor 为 `powersave`。若授权后它们全部变为 `performance`：

- “32 个 governor 完整且全部相同”仍通过；
- 温度、GPU 和 zero-step 构造仍可能通过；
- campaign 创建唯一 claim；
- 第一个 worker 才因 ticket host identity 不同而失败。

GPU driver、affinity、AC record 或其他 ticket-bound host/toolchain 漂移也存在同类反例。这些都能在 claim 前确定，不应消耗一次性日程。

### 3.3 必须修复

动态授权 preflight 必须在创建 lock、raw、claim 或 ledger 前，把当前三份 probe/toolchain/environment 身份与父票据中的 capability binding 逐字段比较。Worker 保留重复核验，但不得成为第一次发现该漂移的位置。

规定负例至少覆盖：

```text
governor map drift but still all-equal
affinity drift
CPU model drift
GPU UUID or driver drift
Python/CuPy/CUDA runtime drift
thread-policy drift
AC record drift
```

这些负例必须证明：

```text
raw / lock / claim / ledger / sample all absent
```

## 4. 阻塞项 P0-2：长日程不能证明每个样本未受后来出现的 CPU 竞争负载污染

### 4.1 当前门集

Campaign 在 claim 前只执行一次 30 秒完整环境门。Claim 后每个样本前只做瞬时检查：

```text
CPU count
governor
AC
Tctl
GPU temperature
other GPU compute process
```

该瞬时门不测量 30 秒背景 CPU，也不枚举具有实际 CPU 增量的其他计算进程。

样本内四个 monitor 只跟踪：

```text
target GPU
target Tctl
target /proc
target pidstat
```

GPU monitor能发现其他 GPU compute process，但没有等价的系统 CPU 背景监测。

### 4.2 风险

18 项日程可能持续数小时。仓库外 CPU 作业可以在 claim 后、两个样本之间或一个长样本内部启动。当前证据仍可能把受污染的墙钟作为 scored baseline。

### 4.3 必须修复

至少同时满足：

1. 每个样本 `mark_sample_running()` 前重新执行完整 30 秒背景环境门；
2. 样本生命周期内增加可审计的 system/background monitor，排除目标、orchestrator 和已登记 monitor PID 后，记录其他进程 CPU 增量与 compute-process 身份；
3. 样本中出现超阈值背景 CPU 或其他计算进程时，样本失败并使 claim 永久 `FAILED_STOPPED_NO_RESUME`；
4. analyser 独立重算该污染门。

允许采用等价实现，但必须直接证明整个 target lifetime 未被未登记 CPU 计算负载污染；仅在样本开始前截取一次 `/proc` 不足以完成该证明。

## 5. 阻塞项 P0-3：CUDA profile 的 telemetry 终点错误使用了外层 Nsight 进程结束时刻

### 5.1 当前对象

CUDA profile 的 `subprocess.Popen` 对象是外层 `nsys profile` 进程；外部 monitor 的 target PID 是内部 Python worker。

Monitor 在 worker 退出时自动停止。可是 orchestrator 在 `nsys` 完成收尾并退出后才记录：

```text
target_end_ns = ended_ns
```

随后用该时刻审计 worker telemetry coverage。

### 5.2 反例

若 worker 在时刻 $t_w$ 正常完成，而 Nsight 用超过 2 秒导出/收尾，在时刻 $t_n$ 才退出：

```text
t_w < t_n
monitor samples end near t_w
coverage target end = t_n
```

当前 `maximum_gap_at_most_2_s` 会把完整的 worker telemetry 错判为截断。轻量最小探针成功不能证明真实 B2/B3 trace 的收尾一定小于 2 秒。

### 5.3 必须修复

必须分离两个时间边界：

```text
worker target lifetime:
  monitor coverage, PID lifetime, target memory/utilization

outer launcher lifetime:
  scored/profile end-to-end wall time, Nsight finalization cost
```

Worker target end必须来自内容寻址的 worker completion/exit observation，而不是外层 profiler 退出。Nsight 的收尾仍应计入 CUDA profile 的外部端到端墙钟和正常退出门。

规定测试必须包含：

```text
worker telemetry 完整 + 人为 5 s profiler finalization lag -> PASS
worker telemetry 在 worker completion 前截断 -> FAIL
outer nsys 非零或收尾异常 -> FAIL
```

## 6. 阻塞项 P0-4：第 18 项先把 ledger 写成 COMPLETE，terminal publication 失败后无法形成合法失败事务

### 6.1 当前顺序

最后一个样本成功后：

```text
mark_sample_pass(index=17)
  -> ledger.status = COMPLETE

publish_execution_complete(...)
  -> O_EXCL 写 execution_complete.json
```

### 6.2 可触发反例

若 `execution_complete.json` 的创建、写入、fsync 或严格重载失败：

1. ledger 已经是 `COMPLETE`；
2. outer exception 尝试 `mark_schedule_failed()`；
3. `mark_schedule_failed()` 拒绝修改 terminal COMPLETE；
4. `publish_execution_failure()` 又要求 ledger 已为 `FAILED_STOPPED`；
5. 最终可能留下：

```text
ledger = COMPLETE
execution_complete = absent or partial/corrupt
execution_failure = absent
```

这与一次性、不可恢复的证据链不相容。

### 6.3 必须修复

最后一个样本 PASS 后不得立即把 ledger 设为最终 COMPLETE。应采用单一、可验证的终态模型，例如：

```text
all 18 entries PASS
ledger status = ALL_SAMPLES_PASS_PENDING_TERMINAL

then either:
  valid execution_complete terminal record
or:
  ledger FAILED_STOPPED + valid execution_failure
```

可以采用其他事务设计，但必须保证所有注入点最终只属于：

```text
A. 18 PASS + 唯一完整 completion
B. 自洽 FAILED_STOPPED + 唯一 failure
```

禁止：

```text
COMPLETE ledger + missing/corrupt completion
COMPLETE ledger + failure
all PASS + no machine-explained terminal state
failure file + nonfailed ledger
```

必须对 completion open/write/fsync/reload、ledger transition 和 failure publication 做故障注入。

## 7. 阻塞项 P0-5：独立 analyser 没有绑定到执行 claim 的 Git 快照，也没有完整的单写入者/失败恢复边界

### 7.1 当前缺口

`analyse_p0p2v2_campaign.py` 会读取 claim、ledger、completion 和 raw manifests，但不会在分析前验证：

```text
symbolic HEAD = main
HEAD = claim.authorization_child_commit
worktree clean
analyser/contract/parsers 的 blob 与 claim.implementation_files 完全一致
formal source and reviewed static identity unchanged
```

因此，在 18 项运行完成后先拉取或提交一版新 analyser，再运行分析，当前代码仍可能生成 compact evidence。该报告将由未授权代码解释旧 raw。

此外，compact publication 没有独占 analysis lock；`DirectoryPublicationTransaction` 在写入或 rename 异常时会留下 staging，但没有 matching transaction journal、回滚或 `analysis_failure.json`。并发 analyser 或外部中断会留下无法由终态解释的隐藏目录。

### 7.2 必须修复

分析前必须：

1. 从 claim 重建 authorization child、review parent、reviewed snapshot 和 implementation blob 绑定；
2. 要求 clean symbolic main，并要求当前 analyser 及全部解析依赖与 claim 中的 implementation files 精确一致；
3. 重新核验 formal source、contract、capability、raw controls 和授权身份；
4. 使用独立 analysis lock 或在 campaign lock 内启动独立 fresh-process analyser；
5. 为 staging、terminal rename 和失败路径建立可恢复事务或明确的失败记录；
6. 在 compact terminal 中记录 analyser commit、blob set、claim SHA-256 和 raw manifest SHA-256。

允许同一授权快照下的确定性事务恢复，但禁止在代码、claim 或 raw 发生变化后重新解释数据。

规定负例至少覆盖：

```text
HEAD changed after schedule
analyser blob changed
worktree dirty
concurrent analyser
unknown stale staging
terminal write failure
terminal rename failure
raw changed after completion
```

## 11. 技术债与性能路线

全项目裁决不变：

```text
TARGETED CROSS-MODULE REFACTOR AFTER BASELINE
PROJECT-WIDE REWRITE REJECTED
```

当前正式 HF3D 结构已经有清晰的 backend、stepper、pressure、recording、timestep、numerics 和 archive 边界。整体重写会同时破坏浮点顺序、失败事务和历史资格证据，风险高于收益。

旧真实运行仍显示硬件利用不足：

```text
16 cores / 32 threads
process CPU near one logical core
GPU mostly 16%--22%
pressure solve with recurrent host-device transfer
```

但 P0-P V1 没有产生样本，P0-P2 V2 尚未授权，所以当前仍没有新的可信端到端 baseline。必须先完成本次执行前补丁和一次合法 baseline，再根据真实热点决定 E0 小优化或显式 GPU-resident E1 backend。线程变量和利用率图不能代替数值等价与端到端加速比。
