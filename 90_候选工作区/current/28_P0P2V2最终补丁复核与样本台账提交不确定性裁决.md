只有工作树仍为空才接受失败登记。因此一次温度、背景进程、机器 identity 或 zero-step probe 的 claim 前失败可以完整保留，同时满足：

对应正负测试已经覆盖多次 preclaim failure、未忽略路径和工作树污染。该部分可以保留。

### 2.2 Analysis 对授权链和当前解析工具链重绑定：接受

当前 analyser 在获取 analysis lock 和创建任何输出之前：

1. 重新调用允许态授权加载和完整 parent-ticket audit；
2. 从 Git objects 重建 C2、P2、reviewed snapshot、ticket blob/hash 和 authorized blob；
3. 将这些值与 claim 中的 child、parent、snapshot、ticket 和 authorized blob逐字段比较；

Failure 使用独立 staging 和原子 no-replace rename；success/failure 互斥、并发 lock loser、重复调用、stale staging、terminal write 和 rename 故障均有测试。该部分可以保留。

## 3. 新阻断：样本 ledger 转换存在“已提交但调用抛错”的不确定状态

### 3.1 持久化原语的实际语义

Ledger 通过 `_publish_ledger()` 调用 `atomic_json()` 更新。`atomic_json()` 的顺序是：

```text
1. 在同目录写临时文件
2. flush + fsync(temporary file)
3. os.replace(temporary, schedule_ledger.json)
4. fsync(parent directory)
```

因此以下情况合法且可构造：

```text
os.replace 已成功
schedule_ledger.json 已经是新候选状态
随后父目录 fsync 或调用返回前的步骤抛出异常
```

异常本身不能说明 ledger 仍是旧状态。

`mark_schedule_failed()` 已部分认识到这种不确定性：异常后会重新加载 ledger；若磁盘内容已经等于候选 failed ledger，就不再把该异常当成转换失败。

但是 `mark_sample_running()` 和 `mark_sample_pass()` 当前没有相同的提交后重读语义。

### 3.2 反例 A：RUNNING 已落盘，但调用抛错

执行器顺序为：

```text
launch_token = mark_sample_running(sequence_index, sample_id)
active_index = sequence_index
active_sample = sample_id
execute_one_sample(...)
```

若 `mark_sample_running()` 已经把 ledger 原子替换为：

```text
entry.state = RUNNING
start_count = 1
launch_token_sha256 = H(token)
```

但父目录 `fsync` 随后抛错，则函数不会返回 token，`active_index` 和 `active_sample` 仍为 `None`。

Outer handler 随后调用：

```text
mark_schedule_failed(sequence_index=None, sample_id=None, ...)
```

但 ledger 中已经存在 RUNNING entry。状态机会正确拒绝“全局失败遗漏 RUNNING sample identity”。`publish_execution_failure()` 又要求 ledger 已经是 `FAILED_STOPPED`。

可能留下：

```text
claim exists
ledger = IN_PROGRESS with one RUNNING entry
no worker started
no sample terminal
no execution_complete
no execution_failure
```

该一次性 claim 无法恢复，也没有唯一失败终态。

### 3.3 反例 B：PASS 已落盘，但调用抛错

样本目录成功发布后，执行器调用 `mark_sample_pass()`。

若 ledger 已经原子替换为：

```text
non-final sample:
  current entry = PASS
  ledger = IN_PROGRESS

final sample:
  all entries = PASS
  ledger = ALL_SAMPLES_PASS_PENDING_TERMINAL
```

但父目录 `fsync` 随后抛错，outer handler 仍保留当前 `active_index`，并尝试把该 entry 从 RUNNING 转为 FAILED。

实际 entry 已经是 PASS，因此 `mark_schedule_failed()` 会拒绝。随后 failure publication 同样因 ledger 非 FAILED 而拒绝。

可能留下：

```text
sample success directory exists
ledger already contains PASS
completed list in orchestrator did not advance
no execution terminal
```

若发生在第 18 项，则会留下全部 PASS、pending terminal、但没有 completion 或 failure。

### 3.4 当前测试为什么没有覆盖

现有 final-ledger 测试把 `_publish_ledger()` 替换为“在写入前直接抛错”。该负例证明了旧 ledger 仍为 RUNNING 时能够转入失败事务。

它没有覆盖：

```text
original_publish(candidate)
raise OSError("post-commit synthetic fault")
```

即“候选 ledger 已经可严格重载，但调用仍抛错”的状态。

同样缺少对普通样本 RUNNING、普通 PASS 和最终 pending-terminal 三种 post-commit fault 的完整 orchestrator 级测试。

## 4. 裁决

**阻塞。** 在一次性、不可恢复的 18 项长日程中，RUNNING/PASS ledger transition 必须具有明确的 commit-point 判定。否则一次本可恢复的父目录 `fsync` 返回错误会产生既非成功、也非失败的悬空 claim。

这不是要求分布式事务或断电后自动恢复，也不是对单用户工具做无限防御；它是现有原子 replace 设计内已经显式处理过的“调用结果不等于持久状态”问题，应在所有关键 ledger transitions 上使用一致语义。

因此本轮不签发 P2 ticket，也不创建 C2 grant。

## 5. 必须完成的最小补丁

允许继续使用现有 V2 contract、schedule、authorization namespace、raw root 和全部已接受实现。不得复制 V3 harness。

### 5.1 统一 ledger transition helper

新增一个内部统一提交函数或等价机制，输入至少包括：

```text
expected_before ledger
candidate_after ledger
transition label
```

它必须：

1. 在写入前验证旧 ledger 精确等于 `expected_before`；
2. 使用原子 replace 路径写入 `candidate_after`；
3. 正常返回前严格重载并确认候选；
4. 若写入调用抛错，立即严格重载最终路径并分类：

   ```text
   observed == candidate_after
     -> transition committed; return recovered-committed

   observed == expected_before
     -> transition not committed; may retry once with the same candidate

   observed is neither, missing, symlink, malformed or unreadable
     -> transition state uncertain; no worker or later sample may start
   ```

5. 重试必须使用同一个 candidate，不得重新生成 launch token、时间戳或 start count；
6. 不得把同一 sample 标为启动两次。

### 5.2 RUNNING 转换

`mark_sample_running()` 必须在本地先生成唯一 token 和完整候选 ledger，再调用统一 transition helper。

若磁盘已经是候选 RUNNING ledger，即使首次调用抛错，也必须把原 token返回给唯一 worker launch；不得生成第二个 token或第二次递增 `start_count`。

若最终状态无法证明为旧 ledger或候选 ledger，必须在 worker 启动前停止，并通过独立、可审计的 terminalization 路径记录 consumed claim；不得误启 worker。

### 5.3 PASS 转换

`mark_sample_pass()` 必须采用同一语义。

若磁盘已经是候选 PASS/pending-terminal ledger，应把样本视为 ledger transition 已提交并继续：

```text
更新 completed list
进入下一项，或发布最终 completion
```

不得再尝试把已 PASS 的 entry改成 RUNNING failure。

若磁盘仍是旧 RUNNING ledger，可使用同一候选重试；重试失败时才进入正常 FAILED_STOPPED 事务。

### 5.4 Outer handler 的防御性恢复

即使 transition helper 内部失败，outer handler 也必须在写 execution failure 前重新读取 ledger，并根据实际 entry 状态选择：

```text
RUNNING -> 带精确 sequence/sample 的失败转换
PASS / ALL_SAMPLES_PASS_PENDING_TERMINAL -> 已提交转换的恢复或明确 terminalization
no RUNNING -> 全局失败转换
```

不得只依赖内存中的 `active_index` 是否已经赋值。

### 5.5 规定测试

至少新增并通过：

1. RUNNING 写入前失败；
2. RUNNING 已原子替换后抛错；
3. RUNNING strict reload 第一次瞬时失败；
4. 普通 PASS 写入前失败；
5. 普通 PASS 已原子替换后抛错；
6. 第 18 项 pending-terminal 写入前失败；
7. 第 18 项 pending-terminal 已原子替换后抛错；
8. 同一 token、`start_count=1`、无第二 worker launch；
9. post-commit PASS 后 completed prefix 正确推进；
10. 无论注入点为何，最终只能是：

   ```text
   A. 合法继续并最终形成唯一 completion
   B. 自洽 FAILED_STOPPED + 唯一 failure
   ```

11. 不允许留下 RUNNING/PASS/pending-terminal 且无 execution terminal 的悬空终态；
12. 完整 orchestrator 模拟，而不只直接调用单个 ledger 函数。
