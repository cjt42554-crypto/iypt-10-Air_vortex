## 2. 上一裁决五项阻断的复核结果

### 2.1 Claim 前完整机器身份：接受

新 preflight 在创建 campaign lock、raw、claim、ledger 或 sample staging 以前：

1. 运行 B1/B2/B3 三个 fresh-process CUDA 零步探针；
2. 取得 post-probe 完整环境；
3. 重建 Python、NumPy、SciPy、CuPy、CUDA runtime/driver、GPU、affinity、线程策略、CPU model、platform、governor、AC、GCC 与 Nsight identity；
4. 与父票据 `toolchain_binding` 做递归、逐字段、逐类型精确比较。

Claim 再登记同一 `preclaim_machine_identity`，并要求它逐值等于票据 toolchain。Governor、affinity、CPU model、driver、GPU UUID 和线程策略漂移已有 claim 前负例。

该部分可以保留。

### 2.2 每样本环境门与背景污染：接受

每个样本在 `mark_sample_running()` 前重新运行完整 30 秒环境门。样本生命周期内增加 background monitor，记录：

```text
/proc process snapshot
aggregate /proc/stat CPU ticks
process parent identity
```

独立审计排除 worker、orchestrator、monitor 及其后代，并同时要求：

```text
system background CPU <= 25% of one logical CPU
no named external compute process >= 5% of one logical CPU
telemetry coverage >= 95%
maximum gap <= 2 s
```

分析器重新从原始 JSONL 计算该门。该部分可以保留。

### 2.3 CUDA worker / Nsight launcher 生命周期：接受

CUDA profile 已将：

```text
inner Python worker lifetime
outer nsys launcher/finalization lifetime
```

分开记录。GPU、CPU、内存和背景 telemetry 只以 worker PID/start ticks 的生命周期为覆盖窗口；outer launcher 只承担端到端 profile wall、正常退出和 finalization lag。

人工 5 秒 finalization lag 可通过，真正的 worker telemetry 截断和 outer launcher 非零退出仍失败。该部分可以保留。

### 2.4 Execution 唯一终态：接受

第 18 项 PASS 后 ledger 进入：

```text
ALL_SAMPLES_PASS_PENDING_TERMINAL
```

而不是提前进入 COMPLETE。成功终态由以下组合定义：

```text
18 entries PASS
ledger = ALL_SAMPLES_PASS_PENDING_TERMINAL
one valid execution_complete.json
no execution_failure.json
```

失败终态为：

```text
ledger = FAILED_STOPPED
one matching execution_failure.json
no execution_complete.json
```

Completion/failure 的 partial file 会隔离，失败 ledger 和 failure record 可在一次性注入错误后恢复；`validate_terminal_execution_state()` 只接受唯一成功或唯一失败组合。该部分可以保留。

### 2.5 Analysis patch：只通过主体，不足以签发授权

Analysis 已增加：

- claim 中 execution child 与当前 HEAD 的比较；
- analyser/parser 文件 blob、formal source 和 contract hash 比较；
- `.analysis.lock`；
- stale staging 拒绝；
- compact evidence staging、terminal-last rename；
- `analysis_failure.json`。

但是当前仍存在三项可实际触发的执行前或分析终态矛盾，见下文。

## 3. P0-6：所谓“非消费 preflight”会使授权快照永久变脏

### 3.1 可触发路径

未来 C2 上的执行流程为：

```text
load_authorization()  # 要求 clean worktree
zero_step_preflight()
preflight gate fails
_publish_preclaim_failure()
```

`_publish_preclaim_failure()` 当前把失败记录写入：

```text
artifacts/p0p2v2/static/preclaim_failures/
```

但候选 `.gitignore` 只忽略：

```text
.p0p2v2_campaign.lock
.analysis.lock
.compact_evidence.staging.*
performance_raw/
```

没有忽略 `static/preclaim_failures/`。

因此一次温度、背景进程、机器 identity 或 zero-step probe 的 claim 前失败会产生未跟踪文件。下一次执行再次调用授权审计时，`git status --porcelain=v2 -z --untracked-files=all` 不再为空，精确 C2 授权会在 preflight 前失败。

结果是：

```text
claim consumed = 0
但授权实际上无法再次使用
```

这与冻结语义：

```text
preflight_consumes_claim = false
```

矛盾。

### 3.2 裁决

**阻塞。** Claim 前失败必须能够完整保留，同时保持同一 C2 工作树清洁、授权仍可进行下一次非消费 preflight。

### 3.3 必须修复

二选一：

1. 把 preclaim failure root 移到精确忽略、与 static review evidence 分离的 runtime-evidence 目录；或
2. 为现有目录增加精确 `.gitignore` 规则。

无论采用哪种方式：

- `.gitignore` 必须进入 future ticket 的 reviewed implementation binding；
- failure 文件必须 O_EXCL、regular、no-symlink、严格 JSON、唯一命名；
- 多次 claim 前失败可以各自保留；
- 不得创建 raw、claim、ledger、sample、campaign lock；
- 写入失败记录后 `git status --porcelain=v2 -z --untracked-files=all` 必须仍为空；
- 同一 C2 随后的合法 preflight 必须仍可通过且 claim 仍为 0。

## 4. P0-7：Analysis lock 的失败者可以污染成功分析

### 4.1 并发反例

当前 `analyse()` 在进入 `.analysis.lock` 前完成 snapshot 检查。若两个 analyser 同时启动：

```text
A 获得 analysis lock并开始生成 compact evidence
B 获取 analysis lock失败
B 的 main() 捕获异常
B 调用 publish_analysis_failure()
A 后续成功发布 compact evidence
```

最终可能同时存在：

```text
compact_evidence/publication_complete.json
analysis_failure.json
```

Lock 阻止了两个 analyser同时计算，却没有阻止未持锁的失败者写全局失败状态。

### 4.2 重复调用反例

成功分析后再次调用 analyser：

```text
compact_evidence 已存在
DirectoryPublicationTransaction.begin() 拒绝
main() 仍写 analysis_failure.json
```

同样会把一个已成功的最终状态污染成“成功 + 失败并存”。

### 4.3 Post-publish 反例

当前 compact 目录 rename 后还会做 reloaded-terminal/hash 检查。若该检查发生异常，最终目录已经存在，随后又会写 `analysis_failure.json`。系统没有机器门定义这两个对象谁优先。

### 4.4 裁决

**阻塞。** Analysis 必须像 execution 一样只有唯一 terminal state；分析锁的未取得者和成功后的重复调用必须无副作用拒绝。

### 4.5 必须修复

- 只有实际持有 `.analysis.lock` 的进程可以发布 global `analysis_failure.json`；
- lock 获取失败、已有合法 compact success、已有 analysis failure 等 precondition rejection 必须无副作用；
- 开始分析前必须要求：

  ```text
  compact evidence absent
  analysis_failure absent
  unknown staging absent
  ```

- 成功和失败必须互斥：

  ```text
  A. one complete compact terminal, no analysis_failure
  B. one analysis_failure, no accepted compact terminal
  ```

- 尽可能把全部严格 reload/hash 验证放在 staging 内、rename 前；
- 若 rename 后仍需验证，必须提供可审计的 quarantine/recovery 语义，不能把已验收的 success 与 failure 同时保留为有效终态；
- analysis failure、terminal write、rename、lock acquisition 和 repeated invocation 都需要独立故障注入测试。

## 5. P0-8：Analyzer 没有独立重建 P2/C2 授权，也没有观察当前解析工具链

### 5.1 当前检查的实际含义

`analysis_git_snapshot()` 当前调用 `execution_binding()` 并检查：

```text
symbolic main
HEAD == claim.authorization_child_commit
worktree clean
implementation_files == claim.implementation_files
formal source == claim.formal_source_tree
```

这些检查有价值。

但所谓 capability gate 当前只是：

```text
claim.preclaim_machine_identity == claim.toolchain_binding
```

它比较的是 claim 内两个历史字段，不观察当前 analyser 使用的 Python、NumPy、SciPy、平台或工具链。

同时 analyser 没有重新调用未来授权对象的：

```text
load_authorization(require_dynamic=True)
或 audit_authorized_repository(...)
```

所以它没有独立验证：

```text
当前 C2 是否仍是合法的 P2 单父授权 child
P2 ticket blob/hash
reviewed snapshot commit/tree
当前 authorized blob
claim 中 ticket/parent/snapshot/blob 是否与 Git object 一致
```

### 5.2 风险

用户可以在正确 C2 上用另一个 Python/NumPy 环境调用 analyser。Git 和 claim gate仍可通过，但：

```text
NPZ decoding
float/dtype handling
statistics
SQLite parsing
canonical payload rebuilding
```

由未绑定的解析工具链执行。

Claim 本身也可能保持 schema 有效，却没有在分析阶段再次与 P2/C2 Git objects 交叉。

### 5.3 裁决

**阻塞。** “Claim-bound analysis”必须同时绑定 Git 授权链和当前解析工具链，不能只比较 claim 内历史字段。

### 5.4 必须修复

分析开始前、获取 analysis lock和创建输出以前：

1. 从当前授权文件重新执行完整 parent-ticket audit；
2. 要求 audit 返回的 C2、P2、reviewed snapshot、ticket blob/hash、authorized blob 与 claim逐字段一致；
3. 要求 claim hash、ledger、completion 和 raw controls 一致；
4. 使用精确受审查 Python 入口运行 analyser，或在 analyser 内重建并比较当前 parser toolchain；
5. 至少绑定：

   ```text
   Python executable / version
   NumPy version
   SciPy version（若解析依赖导入）
   platform/machine
   analyser/parser implementation blobs
   contract/formal source identity
   ```

6. 对 wrong Python、package drift、fake claim parent、wrong ticket blob、wrong authorized blob、HEAD-only-but-invalid-parent-chain 增加负例。
