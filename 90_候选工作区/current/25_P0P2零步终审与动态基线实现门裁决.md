## 6. 授权结构仍需加强

当前未来授权 schema 的总体方向正确，但在签发前还必须关闭以下门：

1. `P2` 本身必须显式要求恰有一个 parent，而不只是 `P2^ == I2`。
2. 必须要求 symbolic `HEAD = refs/heads/main`，不仅是 `HEAD == origin/main`。
3. 授权审计前必须完成 `git fetch --no-tags origin main`，拒绝陈旧 remote-tracking ref。
4. `I2..P2` 和 `P2..C2` 应使用 NUL-safe raw diff，验证 status、mode、old/new blob、rename/copy/symlink/submodule，而不只比较 name-only 路径。
5. ticket、ruling、current/history 应验证为精确 regular `100644` blobs。
6. 必须增加完整的合成 Git 仓库正负测试，覆盖：

```text

wrong branch
```

当前授权专项测试主要覆盖 schema 和最小路径集合，尚未实际证明完整仓库拓扑审计。

## 11. 技术债与硬件利用裁决

### 11.1 技术债

当前仍采用：

```text
TARGETED CROSS-MODULE REFACTOR
```

不采用全项目重写。

关键证据没有变化：正式 HF3D 已拆分 backend、stepper、pressure、timestep、recording、types、numerics 和 archive；整体推倒会破坏冻结浮点顺序、事件、失败事务和数值证据。真正高优先级债务是：

1. 主机 NumPy 热路径和每步 host-device pressure transfer；
2. recording/archive 与未来 device-resident state 的边界；
3. 多套 campaign/evidence framework 的重复；
4. 历史测试与终态授权对象不兼容。

处理顺序：

```text
P0-P2 baseline and profiler
→ explicit accelerated backend
→ recording/archive device boundary
→ future campaign shared evidence core
→ 其他模块仅凭独立证据处理
```

当前不能在基线前修改正式程序。

### 11.2 硬件利用

既有真实运行证据仍为：

```text
16 cores / 32 threads
process CPU ≈ 101%
main thread ≈ 99.9%
GPU mostly ≈ 16%–22%
process CPU time ≈ wall time
pressure solve has host-device transfers each step
```

因此：

```text
CPU utilization adequacy = FAIL
GPU utilization adequacy = FAIL
end-to-end efficiency = FAIL
```

零步构造 PASS 不改变这一裁决，也不能替代 P0-P2 动态 baseline。

### 11.3 后续正式优化方向

P0-P2 完整结果冻结后，优先路线仍为显式新身份的 GPU-resident E1 backend，保留 reference backend。不得静默替换原 backend。

正式提升至少要求：

```text
numerical-equivalence contract frozen before new results
B1/B2/B3 each median speedup >= 1.50x
geometric median >= 2.00x for E1
full production-equivalent window >= 2.00x
no benchmark regression > 5%
median GPU compute utilization >= 45%
p90 GPU utilization >= 70%
full-field H2D/D2H bytes per accepted step reduced >= 75%
peak device memory <= 80% available VRAM
```

利用率不能替代端到端墙钟，线程变量不能替代性能证据。
