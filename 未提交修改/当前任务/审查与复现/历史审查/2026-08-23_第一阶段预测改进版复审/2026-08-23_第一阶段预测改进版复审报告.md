## 五、P0 问题

### P0-1：Stage1 后端注册表结构错误，正常程序不能运行

运行时的 `_BACKEND_IMPORTS` 类型和发现循环要求四元组：

```python
(backend_id, module_name, class_names, aliases)
```

参见：

- `04_第一阶段预测改进版/02_模拟程序/src/airvortex/runtime/registry.py:144-157`
- `04_第一阶段预测改进版/02_模拟程序/src/airvortex/runtime/registry.py:184-189`

Stage1 覆盖层却写入三元组：

```python
registry._BACKEND_IMPORTS = (
    ("forward", "airvortex.stage1.backends", (...)),
    ("high_fidelity", "airvortex.stage1.backends", (...)),
)
```

参见：

```text
04_第一阶段预测改进版/02_模拟程序/src/airvortex/stage1/bootstrap.py:11-14
```

这直接解释了 CLI 自检的四变量解包错误。GUI 后端发现走同一路径。

最低修复要求：

1. 保持四元组并给出别名；
2. 新增 `run_stage1_cli.sh self-check` 硬门；
3. 新增两个后端各一个最小 CLI 运行；
4. 新增 GUI 后端发现测试，不能只测试窗口能否打开。

### P0-2：不同物理观测算子被错误赋予相同身份

Stage1 合同要求共同、预注册的中央半径 `r_c`、外环区域、界面水平和放入磁子后的实测静止自由面 `H0`。

实际前向后端使用：

```python
target_columns = radius <= (
    config.forward.effective_target_radius_m + geometry.grid.dr
)
centre_min = min(profile[target_columns])
outer = radius >= 0.8 * R
depth_from_static = config.container.liquid_depth_m - centre_min
```

参见：

```text
04_第一阶段预测改进版/02_模拟程序/src/airvortex/backends/forward_topology.py:493-504
```

HF3D 使用：

```python
centre = radial <= max(grid.bar_half_length_m, grid.radius_m / radial_bins)
outer = radial >= 0.8 * grid.radius_m
nominal_depression = liquid_height_m - centre_min
```

参见：

```text
04_第一阶段预测改进版/02_模拟程序/src/airvortex/numerics/interface3d.py:618-643
```

默认配置下：

- 容器半径约 `45 mm`；
- 前向有效目标半径约 `3 mm`，另加一格；
- HF3D 中央区域由约 `15 mm` 的磁子半长主导。

因此两个后端取中心最低点的区域明显不同。静止参考量也只是配置高度，不是合同宣称的“放入磁子后实测 H0”。HF3D 原元数据还说明名义下降包含栅格体积偏移语义。

但 Stage1 canonicalizer 仅把旧量改名为：

```text
central_depression_from_static_m
visible_outer_to_center_depth_m
surface_height_range_m
```

然后生成相同合同身份：

```text
04_第一阶段预测改进版/02_模拟程序/src/airvortex/stage1/observables.py:23-38
```

这不是统一物理算子，而是统一名称。它会让程序错误地认证两个不可直接比较的量。

此外，合同承诺的基础量：

```text
central_surface_min_height_m
outer_reference_height_m
```

没有进入实际 canonical 输出，用户不能从存档独立复算深度。

正确修复必须建立两个后端共同调用的唯一观测函数，并由实际参数生成身份，不能在结果产生后硬编码相同身份。

### P0-3：完整身份门可被核心分析和 CLI 绕过

Stage1 的 `assert_observables_compatible()` 只被 GUI guard 和少量测试直接调用。核心归档比较仍执行：

```python
comparison = compare_results(left_view, right_view, name)
```

参见：

```text
04_第一阶段预测改进版/02_模拟程序/src/airvortex/runtime/operations.py:686-699
```

构造反例：

- 两个结果拥有同名 `surface_depth_m`；
- 单位均为 `m`；
- 人为把一个结果的 `reference_surface` 改为另一参考面。

预期应拒绝比较，实际 `compare_results()` 接受并计算：

```text
RMSE = 0.5773502691896257
```

因此 CLI、存档和直接分析 API 仍可能对定义不同的量计算 RMSE、MAE 与偏差。README 所述“GUI/分析比较必须通过完整观测身份门”当前不成立。

身份检查必须成为核心比较 API 的强制前置条件，覆盖：

- `analysis.compare_results`；
- `analysis.compare_series`；
- CLI 存档比较；
- paired backend comparison；
- GUI；
- 导出和报告生成。

## 六、P1 问题

### P1-1：新标准观测量没有正式单位

canonicalizer 创建三个新键，却没有同步补充 `metadata["observable_units"]`。

直接运行前向包装后：

```text
central_depression_from_static_m   unit=None
visible_outer_to_center_depth_m    unit=None
surface_height_range_m             unit=None
```

项目严格分析接口因而拒绝比较这些新量。兼容别名 `surface_depth_m` 仍有单位 `m`，反而成为唯一容易进入比较的路径。

GUI 能从名称后缀推断单位，但会将来源标为 `inferred_from_canonical`；严格比较又拒绝推断单位。新公开合同量因此没有形成可用的定量比较链。

### P1-2：事件状态机和输出采样合同不完整

Stage1 映射表只覆盖：

```text
gas_touches_bar
resolved_channel
channel_reconnect
channel_break
sustained_channel_numerical
first_target_touch
```

前向后端实际还发出：

```text
finite_channel
channel_reconnection
sustained_channel
```

`channel_reconnection` 与映射中的 `channel_reconnect` 也不一致。

合成事件测试结果：

```text
finite_channel          prediction_state=None
channel_reconnection    prediction_state=None
sustained_channel       prediction_state=None
resolved_channel        prediction_state=CONNECTED_RESOLVED
```

`CONNECTED_UNRESOLVED`、`DOMAIN_LIMIT`、`INVALID_MODEL_DOMAIN` 和 `FAILED_NUMERICALLY` 也没有完整的实际生成路径。

前向包装还把用户输出间隔改成积分步长，并直接返回全部稠密结果：

```text
04_第一阶段预测改进版/02_模拟程序/src/airvortex/stage1/backends.py:19-24
```

以 `duration=0.01 s`、请求输出间隔 `0.005 s`、积分步长 `0.001 s` 为例，正常常规序列应约为 3 帧，实际返回 11 帧。

事件证据应保留积分尺度时间分辨率，但普通 observable 和 field 序列应恢复到用户请求的输出间隔。

### P1-3：相机测量算子没有进入预测链，身份还遗漏像素尺寸

相机函数位于：

```text
04_第一阶段预测改进版/02_模拟程序/src/airvortex/stage1/measurement.py
```

除自己的单元测试外，没有后端、CLI、GUI、分析或存档流程调用它。因此当前实际链条仍是：

```text
模型内部自由界面 → 直接显示或比较
```

而不是：

```text
模型自由界面 → 投影 → PSF → 像素化 → 分割 → 与实验图像比较
```

`CameraModel.operator_id` 包含观察轴、PSF 和阈值，却遗漏会改变输出网格的 `pixel_size_m`。两个像素尺寸分别为 `1e-4 m` 和 `2e-4 m` 的相机获得相同 operator ID。

`psf_sigma_pixels=NaN` 也能通过当前 `< 0` 检查，应补充有限性验证。

### P1-4：验证程序不能证明实现通过

验证器当前只运行：

```text
compileall
test_stage1_*.py
可选 test_*.py
```

只要这些进程返回零，就将实现状态提升为 PASS。它没有运行：

- CLI 自检；
- GUI 后端发现；
- 双后端最小算例；
- 单位和事件检查；
- 身份不一致反例；
- 相机端到端链；
- transport/CLS/最宽路径专门测试；
- 存档写入、重读与比较。

因此，即使注册表已经损坏，它在修正 `PYTHONPATH` 后仍会输出 PASS。

### P1-5：新守恒诊断被计算后丢弃

共同输运函数计算了相体积残差、密度残差、动量重映射和 clip/repair 指标。Stage1 后端只保留 clip/repair，输运与 CLS 的动量重映射及守恒残差没有进入 observable、metadata、摘要或 acceptance gate。

直接短 HF3D 结果中也没有这些字段。因此 README 中“显式记录动量重映射”的说法与实际结果不一致。

### P1-6：非活动区零密度引入无效除法警告

Stage1 输运把非活动区域密度设为零，粘性应力计算随后在全数组上先除以密度，再屏蔽非活动区域。普通运行会产生：

```text
RuntimeWarning: invalid value encountered in divide
```

使用 `PYTHONWARNINGS=error` 时，第一个 Stage1 HF3D 步即失败。

应只在活动掩膜内除法，或保持有限正密度，并增加每步有限性断言，不能依赖默认忽略警告。
