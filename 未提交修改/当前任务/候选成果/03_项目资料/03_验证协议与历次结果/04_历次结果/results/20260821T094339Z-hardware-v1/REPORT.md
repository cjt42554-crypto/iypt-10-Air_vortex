# HF3D 液面显示与无损硬件性能优化报告

## 结论

- 中间偏左液面图“不动”的直接软件原因已修复：旧 GUI 在求解结束前拿不到三维自由表面数组，只能继续显示初始/旧帧；这不是液面方程被锁死。
- 现在图中显示的是三维求解器已经完成的真实状态：正式输出时刻一定刷新；若输出间隔很长，还会约每 1 秒墙钟时间提取一次已完成求解步的只读液面快照。没有伪造插值，也没有把预览反馈给求解器。
- 已完成不改变离散方程的 CPU 优化，并把占主导耗时的变密度压力投影移植到 RTX 5060 Laptop GPU 的 FP64 CUDA 路径。
- 48×48×72 固定基准中，压力投影加速 `3.32×`（重复基准）到 `3.80×`（干净环境确认）；完整 HF3D 端到端加速的重复中位数为 `1.92×`，干净环境单次确认为 `1.95×`。
- 程序现在确实使用 GPU，但仍是 CPU/GPU 混合程序，并没有让整块 GPU 持续满载。实算时 1 Hz 粗采样看到约 `37%–43%` GPU 利用率、约 `919 MiB` 显存；这与“压力投影在 GPU、局部守恒律仍在 CPU、每步有主机/设备传输”的结构一致。
- 最终实现验证通过，但物理预测仍为 `NO-GO`：当前动态网格未收敛，最细磁子直径仅 1.875 格（门槛 6 格），且没有封存实验对照。性能加速不等于物理有效性提升。

## 为什么以前看起来卡住

旧数据流只有标量进度，三维表面轮廓只存在于后端最终结果中。因此进度条可能前进、CPU 也在计算，但装置截面图无法取得新轮廓，视觉上一直停在初始平面。

默认 HF3D 配置又非常重：

- 物理时长：10 s；
- 网格：48×48×72，共 165,888 个三维单元；
- 配置最大时间步：0.0002 s，因此名义上至少 50,000 步、至少约 82.94 亿单元步；
- 时间步是自适应的，稳定性限制只会增加实际步数，所以这不是上界。

同网格、100 r/min 短程实测中，推进 0.001 s 物理时间需要 59 个自适应步：CPU 重复中位数 11.212 s，CUDA 重复中位数 5.841 s。若仅作线性量级外推，默认 10 s 物理过程约为 31.1 小时 CPU 或 16.2 小时 CUDA；转速、界面状态和自适应步长会让真实耗时改变，所以这不是承诺 ETA。

默认正式输出间隔是 0.02 s。按上述短程速率，两个正式液面帧之间可能约需 117 s CUDA 墙钟时间。新版本因此在正式输出之间增加了只读实时快照；一次真实长输出间隔探针得到：

```text
正式结果时刻：0, 0.001 s
实时表面时刻：0, 0.000153809, 0.000324707, 0.000495606,
              0.000666504, 0.000837403, 0.001 s
完成步数：59
实际设备：cuda；fallback=False
```

这 5 个中间帧都来自已经完成的离散步，未被写入正式结果时间序列。

## 无损优化边界

以下内容没有改变：控制体网格、MAC 离散拓扑、变密度压力矩阵、界面输运方程、牛顿应力、CSF、边界条件、垂向线块 Jacobi 预条件结构、PCG 相对容差和最大迭代数。

完成的优化包括：

1. 把表面张力和黏性应力中“计算完整三分量梯度后丢弃不用分量”的写法改为定向梯度；黏性应力路径不再产生 18 个无用临时数组。
2. 压力投影复用拓扑、系数和对角工作缓冲，利用已验证的唯一邻接关系直接累加，避免通用重复索引归并开销。
3. 在 NumPy/SciPy 导入前治理 BLAS/OpenMP 线程。该稀疏 PCG/小块预条件任务不是“线程越多越快”；现场线程微基准中 2 线程约 0.1781 s，而 32 线程约 0.4971 s，32 线程反而慢约 2.79×。默认最多 2 线程，用户仍可覆盖。
4. 新增 CuPy FP64 CUDA 压力投影：CSR 系数和 CPU 参考路径一致；垂向分段 LDL 分解/求解使用 CUDA RawKernel；PCG 的容差、上限和历史初值规则不变。
5. GPU 环境采用项目内隔离 `.venv-gpu`，不污染系统 Python。启动脚本只有在真实 FP64 设备运算探测通过后才选用它。

CPU/CUDA 浮点归约顺序不同，因此不要求逐位相同；验收要求相同离散问题、相同收敛行为以及舍入量级的一致结果。

## 基准结果

固定压力基准：48×48×72，129,685 个活跃未知量，890,063 个非零矩阵元，固定随机种子 20260821，`rtol=1e-7`，`maxiter=400`，预热与 CUDA JIT 不计时。测试时主机存在其他负载，因此数字应视为该机器当时的可复现实测，不是空闲实验室峰值。

|---|---:|---:|---:|
| 压力投影，9 次重复中位数 | 0.236744 s | 0.071330 s | 3.31898× |
| PCG 迭代数 | 206 | 206 | 相同 |
| 相对残差 | 9.7888037858e-8 | 9.7888037858e-8 | 差 8.45e-20 |

干净隔离环境再次确认：压力投影 CPU 0.218889 s、CUDA 0.057669 s，`3.79558×`；完整程序 CPU 10.422249 s、CUDA 5.355750 s，`1.94599×`（完整程序各一次，用于环境复核，不替代三次重复中位数）。

数值一致性：

- 单次压力投影 `u_x/u_y/u_z/p` 最大绝对差分别为 `2.44e-19 / 3.52e-19 / 5.15e-19 / 2.44e-15`；
- 完整 59 步后，相场最大绝对差 `1.33e-14`，压力 `8.31e-11 Pa`，三速度分量最大绝对差不超过 `1.43e-13 m/s`；
- CPU/CUDA 最大压力相对残差均约 `9.994793e-8`，最大投影后散度约 `1.14323e-6 s^-1`。

## 硬件利用率该怎样理解

“CPU/GPU 百分比没有 100%”不能直接推出程序卡住或没有利用硬件：

- 压力 PCG 是稀疏、内存带宽敏感任务，过多 CPU 线程会增加调度与同步成本；限制线程是性能优化，不是少用硬件。
- GPU 当前只承担压力投影；界面输运、表面张力、动量局部律、边界处理和诊断仍在 CPU。
- 每个投影仍有一次主机到设备、一次设备到主机的数据交换。
- NVIDIA 消费级 GPU 的 FP64 吞吐本来就远低于 FP32；本程序坚持 FP64 以控制数值差异，没有用混合精度换速度。

进一步的大幅提升仍有空间，例如把界面/动量局部律和时间步状态长期驻留 GPU、融合 stencil kernel、减少每步传输。这些工作可以继续保持同一离散方程，但需要更大规模逐核对照与全流程验证；本轮没有把“部分 GPU”夸成“全 GPU”。

## 使用

```bash
cd "/home/cjt/Desktop/iypt/10 空气涡流"
./run_gui.sh
```

HF3D 的“压力求解设备”默认 `auto`：FP64 探测通过就使用 GPU，否则在结果元数据中记录原因并回退 CPU。`cuda` 会在不可用时直接报错，`cpu` 固定参考路径。

CPU 线程可在启动前显式控制：

```bash
AIRVORTEX_BLAS_THREADS=2 ./run_gui.sh
AIRVORTEX_BLAS_THREADS=inherit ./run_gui.sh
```

正式判断某次运行到底用了什么设备，应查看该次结果中的 `metadata.diagnostics.pressure_accelerator`，不要只看启动页文字。
