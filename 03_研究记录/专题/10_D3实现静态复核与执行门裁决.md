## 2. 可保留的实现主体

以下部分与冻结 D3 科学设计一致，可在 V2 中保留：

1. 六算例矩阵严格为 `G6/G9 × DT0/DT1/DT2`，时间步为 `5.5e-6 / 2.75e-6 / 1.375e-6 s`；配置差异限制在登记的运行时长、输出间隔和时间步字段。
2. 运行器直接调用正式 HF3D 网格、初态、压力投影、事务单步、记录和归档接口，没有复制第二套正式求解器。
3. S1 先于 S2；算例内接受步逐步执行有限值、压力残差、投影散度、CFL、体积平衡、重试次数和真实 CUDA 无回退门。
4. 独立分析器不导入候选运行器，重新构造配置，重载正式归档，重算原生输出时刻、G0 掩膜、来源身份、数值质量门以及 `q/s/u/c` 指标和标签优先级。
5. D2、checkpoint、跨根路径、符号链接和跨提交来源已有明确拒绝逻辑；顶层标签失败闭锁优先级与预注册一致。
6. 当前动态入口仍会在授权布尔值为假时拒绝，仓库中没有伪造 S1–S3 已执行的产物。

这些优点只说明候选实现具有继续修补价值，不足以解除真实 CUDA 执行门。

## 3. 阻塞发现

### P0-1：执行身份没有绑定到本次复核过的候选实现

`execution_identity_audit()` 目前只要求候选文件“已提交”、工作树清洁、正式源码哈希匹配、配置文件精确和 CUDA 可用；它没有要求运行器、分析器、测试、预注册与生成配置的 Git blob 或内容 SHA-256 等于本次静态复核对象。

因此，在同一授权语义下，只要先提交一次候选编排或分析代码修改，后续清洁工作树仍可能通过 S0。静态证据中虽然保存了候选内容哈希，但执行入口没有消费这些哈希。这使“Pro 复核的是哪一份执行代码”无法由机器闭合。

同时，现有预注册把：

```text
real_cuda_dynamic_execution = false
execution_requires_new_pro_review = true
```

冻结在合同中；合同形状审计、静态审计和单元测试又明确要求这两个拒绝状态。直接把预注册中的布尔值改成允许态，会同时破坏当前静态审计和测试语义，也会改写已经冻结的预注册。当前不存在独立、不可与预注册混淆且绑定已复核实现的授权对象。

**裁决：阻塞。** 不得通过直接翻转预注册布尔值解除执行门。

### P0-2：独立分析器没有独立完成初态身份复核

静态 S0 会保存六个算例的网格和初态指纹；运行器在每个算例开始时比较当前初态与 S0。最终分析器对同网格归档掩膜进行了独立比较，但对初态一致性只检查运行器摘要中的：

```text
initial_grid_mask_state_matches_s0 == true
```

它没有自行把 `case_summary.initial_identity` 与 S0 中对应算例的网格、状态和正式 G0 掩膜逐字段比较，也没有独立验证同网格三个时间层的初态指纹完全相同。因而该门仍部分信任被审计运行器的结论布尔值，不满足交接要求中的“独立重载与重算”。

**裁决：阻塞。** 最终分类前必须由分析器独立重算并比较。

### P0-3：阶段台账语义与证据路径校验不足

运行器的台账检查主要验证动作名、中文说明、算例列表和证据字段类型；分析器的预分析台账检查主要验证阶段集合与 `PASS` 状态。当前缺少以下严格门：

- 阶段数组必须恰好按 `S0, S1, S2, S3` 排列，且每个阶段只出现一次；
- `disposition`、`status` 与阶段所处状态必须形成允许状态机；
- S0 通过时证据路径必须精确等于 S0 身份报告；
- S1/S2 通过时证据路径必须精确等于各自登记算例的 `case_summary.json`，不得缺项、重复、换序或加入外来路径；
- 失败阶段的证据、后续未执行阶段和全局失败标记必须相互一致；
- S3 发布前后，raw 台账、跟踪台账、报告与清单之间必须保持精确同义。

现有测试覆盖动作名/说明互换和“未执行却带证据”，但没有覆盖重复阶段、乱序、错误 disposition、错证据路径、缺失或多余算例证据等情况。

**裁决：阻塞。** 阶段台账尚不能作为唯一可审计执行状态机。

### P1-1：算例推进之外的异常没有统一写入阶段失败状态

若异常发生在 `advance_runtime_to_registered_end()` 内，代码能保存失败摘要或部分数组，并停止后续算例。可是以下异常可能直接越过 `_run_one_case()` 的正常摘要路径：

- CUDA/网格/投影准备失败；
- S0 初态指纹不匹配；
- 成功推进后归档组装、重载或写入失败；
- case summary 写入失败。

顶层会尝试写全局 `execution_failure.json`，但相应 S1/S2 台账项可能仍为 `NOT_EXECUTED`，也不一定存在逐算例摘要或可恢复的部分证据。后续执行会被失败标记阻止，因此安全上仍是闭锁的；但证据与台账可能相互矛盾，不能满足“失败即同步保留诊断并标记阶段”的审计要求。

**裁决：执行前必须修复。** 所有动态命令异常都要收敛到唯一的失败事务出口。

### P1-2：诊断分窗的基线定义与预注册公式不一致或至少不明确

预注册定义：

```text
q_L,k(t) = Q_L,k(t) - Q_L,k(0)
```

现有分析器对每个诊断分窗先切片，再调用 `initial_removed()`，因此 `0.005–0.010 s` 分窗实际减去的是 `Q(0.005 s)`，不是 `Q(0)`。测试还明确把这种行为描述为“每个登记窗口重新基线化”。

诊断分窗不能改变顶层标签，所以这不会改变完整窗口的顶层裁决；但会改变分窗指标含义。由于当前尚无 D3 动态数据，必须在见到结果前选择并冻结唯一语义：

- 要么先对完整轨迹按 `Q(t)-Q(0)` 处理，再切片；
- 要么明确修订候选诊断合同，说明分窗使用窗口局部基线且只作非确认性诊断。

不得在看到六算例结果后再选择更有利的版本。

**裁决：执行前必须解决。** 推荐保持预注册原式，先全局去初值再切片。

## 4. 非阻塞但应一并加固的事项

1. 独立分析器除调用正式归档校验外，宜再核对 `case_summary.archive.payloads` 与实际载荷文件的哈希和精确文件集。
2. S3 跟踪证据、raw 台账、清单和两份报告的发布宜使用临时目录与原子提升；中途失败不得留下会阻止可审计重跑的半成品。
3. 独立归档硬门失败时，宜产生明确的 `D3_INCONCLUSIVE_FAIL_CLOSED` 审计报告或等价失败证据，而不是只抛出异常且不发布结论对象。
4. 授权对象不得形成自哈希递归；可绑定授权文件之外的实现集合、父提交和预注册 blob，并由下一次 Pro 裁决生成最终允许态。

这些事项可与 P0/P1 修复在同一 V2 补丁中完成；不得因此放宽任何既有阈值。

## 7. V2 返回复核前的最低验收条件

Codex 必须在不推进真实 HF3D 时间步的条件下证明：

1. 未授权、授权文件缺失、授权对象格式错误、blob/hash 漂移、提交漂移、正式源码漂移、配置漂移均在创建 raw 之前失败。
2. 任何被复核候选文件提交后发生改变，即使工作树清洁，也不能沿用旧授权。
3. 阶段乱序、重复、缺失、错误状态、错误证据路径、额外证据和失败后继续均被拒绝。
4. 网格或初态指纹任一字段、dtype、shape 或 SHA-256 改变时，独立分析器失败闭锁。
5. 算例准备、推进、归档、摘要和阶段提交各位置的注入异常都产生相互一致的失败标记和台账，不运行后续算例。
6. 分窗指标基线定义与机器可读合同、README 和测试完全一致。
7. 既有 33 项测试继续通过，并新增针对本裁决的规定失败用例。
8. Ruff、格式检查、`compileall`、限定 mypy、严格 JSON、Pandoc、Markdown 数学检查（若仓库工具存在）和 `git diff --check` 通过。
9. 静态审计继续实际构造六组正式网格和零步初态，确认 `time_steps_advanced = 0`；可运行 CUDA FP64 探针，但不得调用任何真实动态阶段。
10. 返回 Pro 复核时列出完整候选 blob/hash 集合和唯一清洁 `main` 提交；在下一次 Pro 明确写入允许态之前，所有动态入口仍必须拒绝。
