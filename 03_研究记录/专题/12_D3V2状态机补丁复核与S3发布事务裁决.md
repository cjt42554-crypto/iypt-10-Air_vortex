## 2. 对上一裁决两个阻塞项的结论

上一裁决 `11_D3V2静态复核补充裁决.md` 指出的两个具体反例已经关闭，可以接受。

### 2.1 统一前驱阶段门：接受

新增的共享纯状态机模块使 S1、S2、S3 由同一逻辑验证：目标阶段恰为 `NOT_EXECUTED`；所有前驱阶段逐项为 `EXECUTED/PASS`；前驱证据路径与登记路径精确一致；后继阶段保持 `NOT_EXECUTED`；执行提交、摘要、失败标记和 `automatic_follow_on` 状态一致。

运行器在进入任何算例准备前调用该门，分析器也在 S3 分析前调用同一语义门。S1 不再能够凭孤立 S0 报告越过未提交的 S0 台账状态。

### 2.2 前置拒绝与阶段内失败分离：接受

乱序调用、重复调用、前驱未通过、S0 报告或台账身份漂移、授权或执行身份前置失败，现在以 `D3PreconditionError` 在阶段事务之外拒绝。顶层不会为这类前置拒绝写 `execution_failure.json`、改写台账或创建算例目录。

对于 S0、S1、S2 已进入阶段后的失败，运行器先在内存中构造并验证合法失败台账，再写失败标记和原子替换台账；标记写入或台账提交异常会撤回新标记并保留原台账。规定测试覆盖了孤立 S0、S2 乱序、重复阶段、合法前驱路径和标记/台账写入故障。

因此，上一裁决中的 P0-1 和 P0-2 均已关闭。本轮不要求回退这些修复。

## 3. 剩余阻塞项

### P0-3：S3 最终证据发布不是事务，可能留下虚假的 `COMPLETE/PASS`

S3 独立分析器的成功路径当前按以下顺序修改持久状态：

```text
1. _publish_compact_evidence(runs, final_ledger)
   - 逐文件创建 artifacts/evidence/**
   - 写入 tracked stage_ledger.json，内容已经声明 S3 PASS

2. _write_json(RAW_LEDGER_PATH, final_ledger)
   - 原始阶段台账立即变为 S3 EXECUTED/PASS
   - terminal_state 立即变为 COMPLETE

3. 计算并写入 d3_cross_grid_temporal_manifest.json
4. 写入 d3_cross_grid_temporal_report.json
5. 写入 d3_cross_grid_temporal_report.md
```

分析器的 `main()` 没有与运行器等价的 S3 阶段失败事务或回滚边界；`analyse_final()` 中任何写入、复制、哈希或渲染异常都会直接向外抛出。

这产生两个可复现的证据链反例。

#### 反例 A：compact evidence 中途复制失败

若 S0 或若干算例文件已经复制到 `artifacts/evidence/`，随后某次复制、哈希或 tracked ledger 写入失败：

- `EVIDENCE_ROOT` 会部分存在；
- 原始台账仍可能称 S3 未执行；
- 没有 S3 失败标记；
- 再次运行会被“最终输出已经存在”前置检查阻止；
- 部分文件既不是成功证据，也没有被失败台账登记。

#### 反例 B：原始台账已写 `COMPLETE` 后，报告写入失败

若 compact evidence 已成功，且 `_write_json(RAW_LEDGER_PATH, final_ledger)` 已成功，但清单、JSON 报告或 Markdown 报告写入失败：

- 原始台账与 tracked ledger 都声明 S3 `EXECUTED/PASS`；
- `terminal_state = COMPLETE`；
- 台账引用的 manifest、报告 JSON 或报告 Markdown中至少一个不存在或不完整；
- 没有 `execution_failure.json`；
- 后续复核面对的是“成功台账引用不存在证据”的虚假完成状态。

这不是低概率的数值误差，也不是输出美观问题，而是最终分类与证据链的提交原子性问题。上一裁决明确要求“所有阶段内失败都形成唯一且自洽的失败事务”；S3 已通过共享前置门后发生的复制和报告发布异常正属于阶段内失败。当前实现只闭合了运行器侧 S0–S2，尚未闭合分析器侧 S3。

**裁决：阻塞。** 在 S3 最终发布事务被修复并通过故障注入复核前，不能签发覆盖 S0–S3 的允许态机器授权。

### 5.1 必须完成的实现修复

1. **把 S3 作为正式阶段事务处理。** S3 共享前置门通过之前的拒绝继续保持完全无副作用；通过之后的分析、复制、清单生成、报告生成、最终发布和台账提交异常，必须进入 S3 阶段失败事务。

2. **先暂存，后验证，再提交。** compact evidence、tracked ledger、manifest、报告 JSON、报告 Markdown 和最终 raw ledger 必须先在唯一临时事务根或等价 staging 区生成。不得在文件集尚未完整时让 canonical raw ledger 声明 S3 PASS。

3. **成功提交的最终条件必须同时成立：**全部最终文件已生成；全部 JSON 严格解析通过；报告和清单引用路径精确；tracked ledger 与 raw ledger 的 S3 分类、证据路径和执行提交一致；manifest 的文件集合、大小和 SHA-256 与实际文件一致；所有最终目标是仓库内常规文件或常规目录且不含符号链接；重新加载后的阶段台账语义和证据文件门通过。

4. **raw ledger 的 S3 `PASS/COMPLETE` 必须是最后的成功提交点。** 在其写入之前，canonical raw ledger 应保持 S3 `NOT_EXECUTED`，或由明确、可恢复的事务状态解释；绝不能先写 `COMPLETE` 再补报告。

5. **任何阶段内失败都必须二选一，不能半完成：**回滚本次新建的全部 canonical/staging 输出，并提交一个自洽的 S3 `FAILED_STOPPED` 台账和唯一失败标记；或通过明确的恢复日志/事务清单，使下一次启动能够确定性完成回滚或失败提交。

无论采用哪种实现，禁止留下以下任一状态：

```text
S3 PASS + 缺失证据
S3 NOT_EXECUTED + 无登记的部分最终输出
failure marker 存在 + 台账无失败阶段
台账失败 + failure marker 缺失
tracked ledger 与 raw ledger 分类不一致
```

6. **失败提交本身必须可恢复。** 在写失败标记前先验证候选失败台账合法；若失败标记、台账替换、最终 rename 或清理步骤被注入异常，必须恢复到原始合法状态或留下机器可解释、可继续恢复的事务状态，不能只依赖人工猜测。

7. **禁止复用陈旧 staging 或部分最终输出。** 每次 S3 必须绑定当前执行提交、授权对象、正式源码树和本次事务身份。启动时发现未知或不匹配的 staging/部分输出，应失败闭锁并提供可审计处置，不得把它们拼入新报告。

### 5.2 规定的结果盲故障注入测试

至少新增并实际通过下列测试：

1. 在第一份 compact 文件复制前失败；
2. 在 compact 文件复制中途失败；
3. 在 tracked ledger 写入时失败；
4. 在 compact evidence 完成后、raw ledger 最终提交前失败；
5. 在 manifest 生成或写入时失败；
6. 在报告 JSON 写入时失败；
7. 在报告 Markdown 写入时失败；
8. 在最终目录或文件 rename/原子替换时失败；
9. 在失败标记写入时失败；
10. 在失败台账提交时失败；
11. 重复调用 S3、S2 未通过、授权漂移等前置拒绝仍完全无副作用；
12. 完整成功路径中，只有全部最终证据验证通过后 raw ledger 才转为 S3 PASS/COMPLETE。

每个阶段内故障测试都必须断言最终文件系统恰属于以下两种状态之一：

```text
A. 完整成功：全部证据存在且全部互相验证；
B. 完整失败：S3 FAILED_STOPPED、唯一失败标记、自洽证据路径、无可被误认作成功的部分最终发布。
```

不能只断言“抛出了异常”。
