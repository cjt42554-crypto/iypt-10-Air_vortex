> **2026-08-21 分层说明：** `forward_f1_protocol_v1.json` 与
> `run_forward_f1_validation.py` 才对应已冻结的 F1.0 统一界面前向理论；
> `hf3d_protocol_v1.json` 与 `run_hf3d_validation.py` 对应当前统一平台默认的独立三维 HF3D；
> `forward_protocol_v1.json`–`v5.json` 与 `run_forward_matrix.py` 保留的是旧 M2
> 单值图形模型的历史回归证据，`protocol_v1.json`–`v5.json` 与
> `run_numerical_validation.py` 保留旧 H1 轴对称预览证据。两组历史协议均**不得代表当前 F1.0/HF3D 能力**。
>
> **2026-08-21 公式排版身份修订：** `forward_f1_protocol_v2.json` 与
> `hf3d_protocol_v2.json` 只把规范 Markdown 的字节身份推进到 `MD-MATH-1`；
> 数值硬门和物理声称边界不变，v1 协议及其结果目录保持历史只读。

本目录验证的是**实现与离散化**，不是用计算结果替代实验。尤其：

- “运行稳定”“质量守恒”“散度很小”均不等于物理模型正确；
- Forward 的接触转速是经装置参数标定后才可检验的模型量，目前不是实验确认值；
- HF3D 是真正三维、含实际水平胶囊磁子的局部守恒律实现，但当前动态网格欠分辨且未收敛；“三维”不自动等于“装置级高精度”；
- 收敛只在至少三个离散层级的差值持续下降时报告；不下降就写 `NOT_DEMONSTRATED`。

## 历史协议

[`protocol_v1.json`](./protocol_v1.json) 在 H1 最终接口前冻结了首版案例矩阵；H1 随后把喉道分辨率判据升级为与界面厚度和粗网格尺度共同相关，故首版中固定“两格”的假设被保留为审计记录、但不得用于正式判定。[`protocol_v2.json`](./protocol_v2.json) 以可核验的 v1 哈希作基线，修订喉道构造、跨网格轴对称范数和运行中源码不变性门禁。首轮 core 又暴露 v2 只判 mass repair、未独立判 absolute clipping；[`protocol_v3.json`](./protocol_v3.json) 因而分开两类干预。H1 随后冻结为 clip 与 repair 均 fail-closed，[`protocol_v4.json`](./protocol_v4.json) 固定引用 v3 哈希，把 clip 提升为硬门禁并要求 clip-only、signed 抵消、累计 clip 与 repair-only poison 反例。正式运行使用 v4，同时保存四版协议及 SHA-256；旧运行不覆盖。

正式结果目录会保存完整展开配置、后端构造参数、**不可变执行源码快照**、每案起止源码哈希、Python/NumPy/SciPy/BLAS/操作系统信息、实际命令、墙钟、逐帧 CSV、末态场 CSV、数组摘要哈希和比较结论。若执行快照的案前/案后哈希不一致，整案状态必须是 `INVALID_SOURCE_CHANGED_DURING_RUN`。

## 当前规范运行方式

F1.0 前向后端的正式冻结验证：

```bash
PYTHONPATH=src python3 validation/run_forward_f1_validation.py --protocol validation/forward_f1_protocol_v2.json
```

它会创建不可覆盖的
`validation/results/<UTC时间>-forward-f1-v2/`，并明确把结论限制为
`PASS_NUMERICAL_IMPLEMENTATION_ONLY`。`--quick` 只是烟测，永不产生正式 PASS。

HF3D 的正式冻结验证：

```bash
PYTHONPATH=src python3 validation/run_hf3d_validation.py --protocol validation/hf3d_protocol_v2.json
```

它会创建不可覆盖的 `validation/results/<UTC时间>-hf3d-v2/`。实现硬门全部通过时也仍会单独执行物理 GO 审计；空间收敛、局部解析度或封存实验任一不通过，必须保持物理 `NO-GO`。

以下命令是旧 M2/H1-preview 验证框架：

在项目根目录执行：

```bash
PYTHONPATH=src python3 validation/run_numerical_validation.py --list
PYTHONPATH=src python3 validation/run_numerical_validation.py --suite forward
PYTHONPATH=src python3 validation/run_numerical_validation.py --suite hf-smoke
PYTHONPATH=src python3 validation/run_numerical_validation.py --suite hf-core
PYTHONPATH=src python3 validation/run_numerical_validation.py --suite hf-extended
PYTHONPATH=src python3 validation/run_numerical_validation.py --suite all
```

默认创建不可覆盖的 `validation/results/<UTC时间>-<suite>/`。显式 `--output` 也不得指向已有目录；这防止一次运行悄悄覆盖另一次。每个 H1 案例在独立 Python 进程内运行，峰值 RSS 与墙钟因而不会被前一案例污染。

`hf-smoke` 用于接口冻结后的快速阻断检查；`hf-core` 才含时间步、短时网格、界面厚度与 CLS 压缩敏感性；`hf-extended` 含 3 s 网格序列、1 s 高分辨静水和 10 s 默认网格性能。论文证据包应使用 `all`，或合并同一源码树哈希下的 `forward`、`hf-core`、`hf-extended` 三次运行。

## 当前规范主要输出

- `manifest.json`：协议、源码、环境、命令和案例状态；
- `case_index.csv`：每案墙钟、步数、质量、散度、CFL、修复量和硬门禁；
- `cases/<id>/config.json`、`backend_options.json`：完整输入；
- `cases/<id>/timeseries.csv`、`step_diagnostics.csv`：逐帧与逐步诊断；
- 各案例目录中的配置、逐步诊断、末态场和哈希摘要；HF3D 保存方位平均瞬态与最终完整三维场；
- `cases/<id>/summary.json`：指标、元数据、数组形状与 SHA-256；
- `extrapolation.json`：F1.0 的空间—界面联合外推；
- `projection_check.json`、`time_refinement.json`、`dynamic_grid_audit.json`、`reversal.json`：HF3D 的独立实现与物理 GO 门；
- `acceptance.json`：硬门禁逐项结果，及无预设物理容差项目的 `NOT_DEMONSTRATED`/趋势标签；
- `negative_results.json`：所有失败、未证明或干预占优结果，不能从报告中静默删除。

验证脚本只写 `validation/results/**`；它不修改 `src/`、`tests/` 或 `docs/`。
